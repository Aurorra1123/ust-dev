# 2026-04-22 测试自动化计划

## 文档目标

本文件用于把“哪些高风险场景应该预先做成自动化测试”正式落到仓库中。

目标不是一次性铺满所有测试类型，而是先围绕当前项目最容易在比赛答辩、评委验收和后续改动中出事故的链路，建立一套可逐步落地的自动化测试清单与实施顺序。

本计划重点覆盖：

- 学术空间连续时间与 `5` 分钟隐形缓冲
- 体育设施离散 slot 与组合资源
- 活动抢票高并发与异步建单
- 订单状态机、延迟取消、签到与爽约
- 动态规则引擎
- 前端 a11y / 安全 / 响应式
- Docker / CI / judge / smoke 自动化验收

## 当前仓库测试现状

当前仓库已经具备：

- `pnpm smoke:judge`
- `pnpm smoke:live`
- CI 中的 `prisma:generate / lint / typecheck / test / build`

但当前真实状态仍然是：

- `pnpm test` 只是 workspace 级转发，仓库内没有正式业务测试文件
- 当前自动化主要还是 smoke，而不是业务正确性回归
- 异步骨干 `Redis + BullMQ + Worker` 还没有被系统性测试覆盖
- 前端没有浏览器级 E2E、axe、Lighthouse 证据

因此，本计划的核心不是“再补几条 smoke”，而是把最容易暴露架构缺陷的场景分层固化。

## 分层策略

为避免一开始引入过重测试体系，本计划采用四层推进。

### 第一层：API 集成测试

目标：

- 直接验证后端主流程与数据库约束
- 覆盖缓冲冲突、slot 唯一、规则命中、权限边界、抢票唯一性

适合放入的内容：

- 预约创建
- 活动报名
- 规则生效
- 订单查询与取消权限
- 认证与越权边界

特点：

- 回报最高
- 不依赖浏览器
- 最适合先形成第一批稳定回归

### 第二层：系统级异步测试

目标：

- 覆盖 `Redis + BullMQ + Worker + PostgreSQL` 之间的一致性
- 验证 worker 缺失、重启、rehydrate、延迟任务执行等问题

适合放入的内容：

- 抢票并发
- pending 库存补偿
- 订单延迟取消
- 签到后不应误判爽约
- worker 下线后 smoke 应能识别异步骨干缺失

特点：

- 更接近比赛真实演示环境
- 能覆盖纯 service 层看不出的部署级问题

### 第三层：浏览器级 E2E 与非功能测试

目标：

- 覆盖用户端与管理端的关键前端主路径
- 固化 a11y、键盘导航、移动端响应式和前端越权拦截

适合放入的内容：

- 登录
- 学术预约
- 体育预约
- 订单时间展示
- 管理端表单
- axe 扫描
- 移动端 viewport 检查

特点：

- 最适合补齐比赛题面里的 WCAG / 响应式 / 主路径体验证据

### 第四层：红灯规格测试

目标：

- 把当前题面要求但项目尚未完整落地的能力，先写成“应失败或待实现”的规格清单
- 避免后续继续误判为“已经完成”

当前应单列为红灯规格的内容：

- 真实支付闭环
- `PENDING_CONFIRMATION + expireAt` 主创建入口
- 幽灵支付真实对撞
- 爽约扣分、`UserCreditLog` 与规则接管处罚

## 第一阶段建议落地范围

不建议一开始同时补全所有测试类型。第一阶段应先拿下最值钱、最容易暴露架构缺陷的一批。

推荐首批 `12` 项：

1. `API-001` 学术预约缓冲贴脸冲突
2. `API-002` 学术预约缓冲精确边界放行
3. `API-004` 学术同房同段并发仅一单成功
4. `API-007` 体育同场同 slot 并发仅一单成功
5. `API-008` 组合预约任一成员冲突则整单失败
6. `API-009` 单场与组合资源并发对撞
7. `API-010` 同用户并发抢同票仍只保留一条有效报名
8. `API-011` 超库存高并发下绝不超卖
9. `API-013` 学术最大时长规则边界值
10. `API-015` 规则停用后立即失效、启用后立即生效
11. `API-018` 同伴用户不得取消 host 订单
12. `API-020` 任意学生邮箱 + demo 学生密码登录

这批的特点是：

- 都是当前真实代码已经存在的链路
- 一旦回归，现场会非常明显
- 不依赖尚未落地的支付模块
- 回报远高于先写普通 CRUD 单测

## 分阶段实施计划

### Phase 1：先建立 API 集成测试骨架

目标：

- 先把 `API-001` ~ `API-020` 中的 P0 项纳入自动化

完成标准：

- 至少落地首批 `12` 项中的大部分
- `pnpm test` 不再只是空跑
- CI 能对预约、抢票、规则、安全边界产生真实阻断

### Phase 2：补异步系统测试

目标：

- 把 `SYS-001` ~ `SYS-008` 中的 P0 项纳入 `docker compose` 或等价系统环境测试

完成标准：

- worker 缺失、延迟任务失效、库存悬挂这类问题能被自动发现
- judge / smoke 不再只检查“站点是否能打开”

### Phase 3：补浏览器级 E2E 与 a11y

目标：

- 落地 `E2E-001` ~ `E2E-006`

完成标准：

- 至少对学生端一条主路径和管理员端一条主路径形成浏览器级回归
- 能产出明确的 axe / 移动端视口验收记录

### Phase 4：红灯规格转绿

目标：

- 随支付闭环、`PENDING_CONFIRMATION` 主链路和处罚系统补完，把 `RED-*` 逐步转为常规回归测试

完成标准：

- 真实支付与超时取消对撞可自动化复现
- `PaymentRecord / expireAt / UserCreditLog` 都进入真实业务主链路

## 建议的落点

本计划当前只定义“做什么”，不强绑某个具体框架实现。

但为了后续真正落地，建议按以下边界组织：

- 后端 API 集成测试：
  - 预约
  - 活动抢票
  - 规则引擎
  - 安全边界
- 系统级异步测试：
  - Docker Compose 环境
  - Redis / Worker / BullMQ / PostgreSQL 联动
- 浏览器级 E2E：
  - 用户端关键路径
  - 管理端关键表单
  - axe / viewport 检查
- smoke 扩展：
  - 继续保留最小连通性验证
  - 不再让 smoke 充当全部业务回归

## 结论

一句话总结：

- 当前项目最缺的不是“再多写几条 smoke”
- 而是把最容易暴露架构缺陷的业务链路，正式升级为可重复执行的自动化回归

按当前项目真实边界，最应该优先自动化的是：

- 缓冲冲突
- slot 唯一与组合资源原子性
- 抢票并发不超卖
- 规则即时生效
- 越权边界
- demo 认证后门
- worker / delayed job / judge 验收的异步骨干

这几类一旦补齐，项目的比赛答辩可信度、回归稳定性和现场演示抗风险能力都会明显提升。
