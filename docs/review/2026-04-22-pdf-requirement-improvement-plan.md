## 文档目标

本文件用于把当前项目的审查结论，翻译成一份可以直接执行的整改计划。

## 一句话判断

当前项目最需要补的不是“普通功能数量”，而是以下五类高分链路的闭环与证据：

1. 统一订单状态机真正进入主链路
2. 热门活动在高并发下绝不超卖且不把热点压回数据库
3. 动态规则从“固定开关”升级到“可扩展执行”
4. 前端形成响应式、`WCAG 2.2`、`Core Web Vitals` 的可验收证据
5. `Docker Compose`、CI、smoke、集成测试形成真实自动化验收

## 改造原则

1. 不推翻现有单机方案，不引入 Kafka、微服务拆分或外部重型组件。
2. 优先补“评委一定会追问且现在会失分”的链路，不先做表层 UI 美化。
3. 核心约束继续坚持“数据库兜底 + 业务层预检 + 异步补偿”三层保护。
4. 每补一段关键链路，必须同步补自动化测试和验证文档，不接受“代码看起来有了但无法证明”。
5. 支付只做 `Mock Payment` 即可，不必接真实第三方，但必须把回调、幂等、CAS、幽灵支付流程做真。
6. 规则引擎优先采用“责任链 + 规则元数据”的可扩展实现，不在比赛周期内引入不必要的通用脚本沙箱。

## 分阶段整改计划

### Phase 0：先保住已经做对的部分

这一阶段不追求加分，目标是避免后续重构把当前已有亮点打坏。

### 任务

- 把学术空间 `5` 分钟缓冲、体育 slot 唯一、活动报名唯一性先固化为自动化测试。
- 把当前正确的数据库约束和迁移规则写进验证文档，不允许后续“为兼容 pending 状态”误删约束。
- 先冻结一版关键数据样本和演示账号，避免后续整改时答辩素材漂移。

### 完成标准

- `docs/review/2026-04-22-test-automation-plan.md` 中首批保护性用例进入真实测试。
- 当前三个强项都能证明“不是只靠前端判断”。

### Phase 1：补齐统一订单状态机与幽灵支付

这是当前最优先的 `P0`。不先补这一段，项目很难摆脱“演示项目”定位。

### 目标

- 建单不能再直接写 `CONFIRMED`
- `PENDING_CONFIRMATION` 与 `expireAt` 进入真实主链路
- 延迟取消任务真正由生产者创建
- 支付成功与超时取消并发对撞时，只允许一个状态迁移成功

### 任务

#### `ORD-001` 统一建单入口

- 学术、体育、活动三个创建入口不再各自直写终态。
- 新建统一建单编排层，只负责：
  - 创建 `Order`
  - 创建 `OrderItem`
  - 创建业务子记录的“预占中”事实
  - 写入 `expireAt`
  - 投递 `order-expiration` delayed job

#### `ORD-002` 为业务子记录补“预占中 / 已确认 / 已释放”语义

- 学术预约、体育 slot、活动报名都要能表达“已占位但未完成确认”。
- 数据库唯一约束和排斥约束必须继续覆盖“未释放占用”，避免 pending 期间被他人抢走。
- 只有确认成功后，才允许进入签到/爽约链路。

#### `ORD-003` 新增 `payment` 模块，采用 `Mock Payment`

- 新增模拟支付创建接口、模拟支付成功回调、支付查询接口。
- 回调必须写入 `PaymentRecord`，并通过 `OrdersService.transitionOrder()` 驱动状态迁移。
- 业务模块不得直接跳过状态机改订单状态。

#### `ORD-004` 把超时取消接到真实生产者

- 订单创建成功后立即调度延迟取消任务。
- 取消 worker 只处理仍处于 `PENDING_CONFIRMATION` 的订单。
- 取消成功后同步释放学术/体育/活动占位。

#### `ORD-005` 处理幽灵支付

- 支付回调和超时取消都走 `version + status` CAS。
- 谁先成功，谁成为最终事实；后到达的一方只能记录结果，不能覆盖状态。
- 若回调晚于取消，必须记录为“幽灵支付”并触发自动退款或人工补偿队列。
- 即使是 `Mock Payment`，也必须保留完整日志和状态证据。

#### `ORD-006` 统一签到与爽约入口

- 只有 `CONFIRMED` 的预约订单才能进入签到窗口。
- 爽约判定和信用处罚不再绕开订单状态机私下写状态。
- `NO_SHOW` 迁移同样走统一 CAS 和日志。

### 影响模块

- `apps/api/src/modules/reservation/`
- `apps/api/src/modules/activities/`
- `apps/api/src/modules/orders/`
- `apps/api/src/modules/payment/`（新增）
- `apps/api/src/worker.module.ts`
- `apps/api/prisma/schema.prisma`
- `apps/api/prisma/migrations/`

### 验收标准

- 至少一条订单主链路真实经历 `PENDING_CONFIRMATION -> CONFIRMED`
- 至少一条订单主链路真实经历 `PENDING_CONFIRMATION -> CANCELLED`
- 存在“支付成功晚于超时取消”的自动化测试，且最终不会出现双成功
- `PaymentRecord` 不再只是空模型

### Phase 2：修补活动高并发与库存一致性

这一阶段决定你在“绝不超卖”上能不能站稳。

### 目标

- Redis 只负责削峰与热点闸门，不承担不可恢复的最终真相
- 数据库继续做最终库存硬兜底
- 库存补偿不能把售罄热点重新导回数据库
- 活动总额度与票种库存必须一致

### 任务

#### `ACT-001` 强化 `totalQuota` 约束

- 创建/更新活动时校验：
  - `totalQuota >= sum(ticket.stock)` 或明确规定 `totalQuota == sum(ticket.stock)`
- 报名与展示都以统一口径计算剩余容量。
- 管理端保存活动时必须实时提示额度不一致。

#### `ACT-002` 重写 Redis 补偿策略

- 预扣成功后必须生成带拥有者信息的 pending 标记，禁止无归属 `INCR`。
- 只有当 worker 明确判定“本次 job 未落库成功且 pending 仍归当前 job 所有”时，才允许回补。
- 售罄后要能在 Redis 侧快速失败，避免重复把请求放进队列。

#### `ACT-003` 增加库存冷恢复与对账

- 当 Redis 剩余库存 key 丢失或过期时，系统必须能按数据库事实重建。
- 增加定时对账任务或管理员修复命令：
  - 对比 `ticket.stock`
  - 对比 `ticket.reserved`
  - 对比 Redis `remaining`
  - 修复悬挂 pending

#### `ACT-004` 死信与异常回查

- worker 多次失败的任务必须进入死信或错误队列。
- 管理后台至少能看到：
  - 当前票种剩余
  - 异常任务数
  - 最近补偿记录

#### `ACT-005` 系统级并发测试

- 压测和自动化测试必须覆盖：
  - 同用户并发重复抢票
  - 多用户超库存抢票
  - worker 下线
  - Redis key 丢失
  - 容器重启后库存恢复

### 影响模块

- `apps/api/src/modules/activities/`
- `apps/api/src/modules/orders/`
- `apps/api/src/worker.module.ts`
- Redis Lua 脚本
- 管理端活动管理页面

### 验收标准

- 并发超库存时，数据库中 `reserved` 永远不超过 `stock`
- Redis 冷丢失后不会虚增可售库存
- 售罄后热点请求不会持续冲击数据库
- `totalQuota` 与票种库存口径一致

### Phase 3：把规则引擎补到“可扩展且可追责”

当前规则已经脱离主流程 if-else，但还不够动态，评委会继续追问。

### 目标

- 新增规则时，不再修改预约/活动主流程
- 规则可以作用于多个事件点，而不只是预约创建
- 爽约处罚、信用分、资格限制形成一条闭环

### 任务

#### `RUL-001` 从固定 `switch` 改成责任链注册表

- 设计统一 `RuleChecker` 接口和注册表。
- 主流程只做三件事：
  - 构造上下文
  - 读取绑定规则
  - 顺序执行责任链
- 新增规则时只新增 checker 并注册，不改预约/活动 service 主流程。

#### `RUL-002` 扩展规则作用域

- 规则不只用于预约创建，还要覆盖：
  - 活动报名资格
  - 订单取消限制
  - 爽约后处罚
  - 信用分门槛

#### `RUL-003` 信用分与处罚真正接管业务

- `UserCreditLog` 进入真实主链路。
- 爽约不再只写局部限制表，还要记录信用变化。
- 资源禁用、预约次数限制等结果都应来自规则执行结果，而不是散在业务模块里。

#### `RUL-004` 管理端规则校验与即时生效

- 规则配置保存前做结构校验。
- 规则启停、绑定、解绑要立即影响运行时判定。
- 至少提供一组可用于演示的规则模板：
  - 最低信用分
  - 最长预约时长
  - 指定角色才可预约
  - 连续爽约后限制预约

### 影响模块

- `apps/api/src/modules/rules/`
- `apps/api/src/modules/reservation/`
- `apps/api/src/modules/activities/`
- `apps/api/src/modules/orders/`
- `apps/api/src/modules/user/`
- 管理端规则配置页

### 验收标准

- 新增一个规则类型时，不需要改预约/活动主流程文件
- 爽约后会产生真实 `UserCreditLog`
- 规则停用后立即失效，启用后立即生效

### Phase 4：补前端响应式、无障碍和性能证据

这一阶段不是“修一点样式”，而是把 PDF 里的 Web 标准要求做成可量化结果。

### 目标

- 核心页面在手机上可完整操作，不靠横向滚动硬撑
- 核心表单和交互满足最低无障碍要求
- 能给出 `Lighthouse / axe / Web Vitals` 证据

### 任务

#### `WEB-001` 重构移动端核心预约视图

- 学术时间轴和体育排班在小屏下切换成：
  - 卡片列表
  - 折叠时间段
  - 可聚焦的 slot 列表
- 不能再以 `min-w-[780px] / min-w-[860px]` 作为主要移动端方案。

#### `WEB-002` 系统性修补 a11y

- 所有核心表单补显式 `label`
- 建立统一 `focus-visible` 样式，去除“只剩 hover、没有焦点”的状态
- 重要按钮、弹层、切换组件补全键盘可达性和语义属性
- 对错误提示、成功提示、加载状态做语义化处理

#### `WEB-003` 建立性能预算

- 首页和关键业务页图片补尺寸占位，降低 CLS 风险。
- 做最小代码拆分，避免主包继续膨胀。
- 增加前端性能预算，例如：
  - 核心首屏 JS 包体积上限
  - `Lighthouse` 目标阈值
  - `Web Vitals` 采样输出

#### `WEB-004` 非功能自动化留证

- 引入 Playwright 级核心路径回归。
- 接入 `axe` 扫描学生端和管理端关键表单。
- 接入 `Lighthouse CI` 或等价脚本，产出 HTML/JSON 报告。

### 影响模块

- `apps/web/src/ui/pages/spaces/`
- `apps/web/src/ui/pages/sports/`
- `apps/web/src/ui/pages/service-requests-page.tsx`

- `320px` 和 `390px` 宽度下核心页面不横向溢出
- 学生端与管理端关键页面 `axe serious/critical = 0`
- 存在 `Lighthouse` 或等价性能报告，并达到团队定义阈值

### Phase 5：把 DevOps 和自动化验收做成真实门槛

这是把“可以运行”升级为“可以交付”的阶段。

### 目标

- `pnpm test` 不再空跑
- CI 会因为核心业务回归失败而阻断
- `Docker Compose judge` 能重复执行且可留证

### 任务

#### `OPS-001` 接入真实测试脚本

- API 集成测试优先落地：
  - 学术缓冲冲突
  - 体育 slot/组合冲突
  - 活动绝不超卖
  - 规则即时生效
  - 幽灵支付
- 浏览器级 E2E 和 `axe` 作为第二层补充。

#### `OPS-002` 扩充 smoke 与 judge

- `scripts/smoke-judge.mjs` 不再只测首页、登录、健康检查。
- 至少覆盖：
  - 一次学术预约
  - 一次体育预约
  - 一次活动抢票
  - 一次订单取消或确认
  - 一次规则命中

#### `OPS-003` 保证安装和启动可重复

- CI 与镜像构建改为锁定安装，不再使用 `--no-frozen-lockfile`。
- `judge-up` 连续执行必须幂等。
- 容器重启后 worker、延迟任务、库存状态能恢复。

#### `OPS-004` 建立验证文档矩阵

- 每补完一块关键能力，就在 `docs/verification/` 留下：
  - 执行命令
  - 数据准备
  - 结果截图或日志摘要
  - 风险与剩余问题

### 验收标准

- `pnpm test` 包含真实用例且能在 CI 中失败阻断
- `docker compose` judge 路径可重复执行
- smoke 失败时能暴露异步骨干缺失，而不是只证明页面能打开

### Phase 6：把创新点和答辩表达重新包装

当前项目不是没有亮点，而是亮点还没有被整理成“评委一眼能理解”的表达。

### 目标

- 把真实技术亮点和修复后的硬能力做成演示脚本
- 避免答辩时陷入“代码很多，但重点不清楚”

### 任务

- 准备三条标准演示线：
  - 学术空间：连续时间 + `5` 分钟缓冲 + 数据库防重叠
  - 体育设施：组合资源 + 原子失败
  - 热门活动：Redis 预扣 + MQ 削峰 + worker 建单 + 绝不超卖
- 准备一条“硬核演示线”：
  - 创建 `PENDING_CONFIRMATION` 订单
  - 触发支付成功
  - 演示超时取消 / 幽灵支付对撞
  - 展示状态日志和 `PaymentRecord`
- 准备一页“规则引擎”演示：
  - 管理端开关规则
  - 前端立即被限制
  - 爽约后信用变化再影响下一次预约

### 完成标准

- 演示按脚本执行，不依赖临场口头解释
- 每个亮点都有对应代码、日志、测试或验证文档支撑

## 关键模块触点

为了避免后续执行时范围失控，建议按下面的边界拆任务：

| 主题 | 后端模块 | 前端模块 | 交付物 |
| --- | --- | --- | --- |
| 订单状态机与支付 | `orders`、`payment`、`reservation`、`activities`、worker、Prisma | 我的订单、订单详情、支付页或支付弹层 | API、worker、集成测试、验证文档 |
| 活动高并发 | `activities`、Redis Lua、worker、Prisma | 活动详情、抢票状态反馈、管理端活动页 | 并发测试、库存对账、异常处理文档 |
| 规则引擎 | `rules`、`reservation`、`activities`、`user` | 管理端规则页、前端错误提示 | 规则链、模板、单测、演示数据 |
| Web 标准 | 无 | 学术/体育/工单/管理表单/AppShell | Playwright、axe、Lighthouse 报告 |
| DevOps | CI、Compose、judge、smoke | 无 | CI、运行脚本、verification 文档 |

## 推荐执行顺序

推荐顺序不是按模块分，而是按“最能抬分、依赖最强”的路径分。

1. 先做 `Phase 1`，因为订单状态机和幽灵支付是当前最大失分点。
2. 并行推进 `Phase 2` 的活动库存一致性，因为它与支付模块耦合较低。
3. 在 `Phase 1` 稳定后推进 `Phase 3`，把处罚和信用分纳入规则引擎。
4. 在后端主链路稳定后做 `Phase 4` 和 `Phase 5`，避免前端和自动化脚本频繁返工。
5. 最后统一整理 `Phase 6` 的答辩表达和验证证据。

## 当前不建议投入的方向

以下方向会增加复杂度，但对当前比赛得分帮助有限，暂不建议优先做：

- 接入真实第三方支付平台
- 引入微服务拆分或新消息中间件
- 做通用脚本沙箱式规则引擎
- 重做整站设计语言
- 引入重量级监控平台替代当前最小留证方案

## 阶段完成定义

只有同时满足下面四条，才能判断“这次整改真正达到了比赛 PDF 要求”，而不是只写了更多代码：

1. 关键主链路都能跑通：
   - 学术预约
   - 体育预约
   - 活动抢票
   - `PENDING_CONFIRMATION -> CONFIRMED/CANCELLED`
   - 爽约处罚
2. 关键风险都能被自动化发现：
   - 缓冲冲突
   - slot 冲突
   - 绝不超卖
   - 幽灵支付
   - 规则即时生效
3. 前端非功能要求有量化证据：
   - 响应式
   - `WCAG 2.2`
   - `Core Web Vitals`
4. 交付路径可复现：
   - `Docker Compose judge` 一键拉起
   - CI 自动阻断回归
   - `docs/verification/` 有完整留证

## 结论

如果只补表面页面和少量文档，项目仍然会停留在“完成度不错的演示项目”。

如果按本文顺序把 `Phase 1` 到 `Phase 5` 做实，尤其是真正补齐 `PENDING_CONFIRMATION / PaymentRecord / 幽灵支付 / 活动库存自愈 / 规则责任链 / Web 标准证据 / 自动化验收`，那么项目才有机会从当前的 `57 / 100` 抬升到具备终验竞争力的区间。
