## A. 总体结论

层级判断：`有明显缺口`

判断依据：

- 项目已经具备完整演示能力
- 但比赛高分点中，`幽灵支付 / 待支付闭环 / 自动化测试 / WCAG 2.2 / Core Web Vitals 证据` 仍有明显短板
- 当前状态更接近“完成度较高的演示项目”，还不是“终验可稳拿奖”的版本

## B. 六个评分项逐项打分

### 1. 系统架构与领域建模：14 / 20

扣分原因：

- 资源域建模总体正确，`Resource / ResourceUnit / ResourceGroup` 分层成立
- 学术空间与体育设施调度模型已分开，不是扁平表凑合
- 但活动域里的 `totalQuota` 只是展示和管理字段，没有形成强约束
- 支付子域只有模型，没有进入真实业务主链路

### 2. 高并发与状态机处理：8 / 20

扣分原因：

- 有 Redis Lua、BullMQ、独立 worker、CAS 版本号、状态日志，这些方向正确
- 但真实建单路径几乎都直接落 `CONFIRMED`
- `PENDING_CONFIRMATION + expireAt + 支付确认 + 幽灵支付` 没有进入正式主链路
- 抢票缓存补偿策略存在把压力重新打回数据库的风险

### 3. 产品体验与 Web 标准：11 / 20

扣分原因：

- 界面完成度和视觉统一性较好
- 但移动端核心预约主路径仍依赖大宽表和横向滚动
- WCAG 2.2 缺口明显，特别是焦点可见性与表单可访问性
- 没有 Lighthouse / CWV / a11y 的可追溯证据

### 4. 动态规则与代码质量：8 / 15

扣分原因：

- 规则已经从主流程 if-else 中抽出来，这是加分项
- 但当前仍是固定 `switch + 固定 ruleType`，不是强扩展的规则平台
- 规则数量和上下文维度都偏少
- 仓库缺少对应单元测试

### 5. DevOps 与自动化验收：9 / 15

扣分原因：

- Compose、judge 脚本、CI、smoke 脚本都已具备
- 但 `pnpm test` 实际为空跑
- smoke 覆盖面太浅，没有压中比赛关键流程
- 本轮未完成 Docker Compose 现场拉起验证，因此只能给中等分

### 6. 创新性与展示表达：7 / 10

扣分原因：

- 连续时间预约、组合资源、抢票异步化、双端工作台组合起来有展示价值
- 但最能体现比赛技术深度的支付一致性与规则平台化仍不够硬
- 展示亮点有，但还没有形成特别强的技术壁垒

## C. 最严重的 10 个问题

### 1. 严重

问题：所有真实下单主路径都直接把订单写成 `CONFIRMED`

影响：

- `PENDING_CONFIRMATION`
- `expireAt`
- `PaymentRecord`
- 幽灵支付处理

这些关键能力没有进入真实业务闭环，状态机高分项会直接失血。

关键位置：

- `apps/api/src/modules/reservation/reservation.service.ts`
- `apps/api/src/modules/activities/activity-registration.service.ts`
- `apps/api/prisma/schema.prisma`

### 2. 严重

问题：幽灵支付实际上没有完成

影响：

- 没有支付模块
- 没有支付回调入口
- 没有真实写入 `PaymentRecord` 的主链路
- 没有支付成功和超时取消并发对撞的处理证据

这会直接影响评委对订单状态机成熟度的判断。

### 3. 高

问题：活动抢票缓存补偿策略可能把热点重新压回数据库

影响：

- Redis 预扣失败补偿会把库存加回
- Redis 库存 key 只做 `NX` 初始化
- 在 DB 侧频繁冲突时，请求仍可能不断进入异步建单链路

结果是“看起来削峰”，但高并发极限下仍可能把压力打回数据库。

关键位置：

- `apps/api/src/modules/activities/activity-inventory-cache.service.ts`
- `apps/api/src/modules/activities/activity-registration.service.ts`

### 4. 高

问题：`totalQuota` 没有形成真实业务约束

影响：

- 活动总额度与票种库存总和可能不一致
- 后端没有在创建或更新活动时校验额度关系
- 评委追问“总额度和票种库存冲突时以谁为准”时会比较被动

### 5. 高

问题：仓库没有真实自动化测试

影响：

- CI 中的 `pnpm test` 实际空跑
- 当前仓库测试文件数量为 `0`
- 比赛要求中的自动化验收只能算“框架存在”，不能算“真正建立”

### 6. 高

问题：规则引擎扩展性仍然偏弱

影响：

- 只有 3 种固定规则
- 新增规则类型必须改代码重新发布
- 更接近“规则配置化”，还不是强动态的规则引擎

### 7. 高

问题：移动端响应式不足

影响：

- 学术时间轴和体育排班都依赖固定最小宽度
- 移动端核心预约操作大量依赖横向滚动
- 在 Web 大赛评委口径下，这类实现一般只能算“勉强可用”

### 8. 高

问题：WCAG 2.2 缺口明显

影响：

- 部分表单没有显式 label，只靠 placeholder
- 大量交互使用 `outline-none`
- 缺少系统性的焦点可见性和键盘可达性设计

### 9. 中

问题：Core Web Vitals 没有证据链

影响：

- 没有 Lighthouse / Web Vitals / 性能回归脚本
- 主包体积已不算小
- 首页通知图片没有宽高占位，存在 CLS 风险

### 10. 中

问题：smoke 验收覆盖过浅

影响：

- 只验证了首页、健康检查、登录、资源和规则读取
- 没有覆盖预约冲突、活动抢票、取消、签到、规则生效、状态机分支
- 不能支撑“关键业务自动化验收”这一评分项

## D. 最值得保住的 5 个优点

1. 学术空间预约真的把 5 分钟缓冲下沉到了数据库排斥约束，不是只在前端提示。
2. 体育设施按 1 小时 slot 建模，并用部分唯一索引兜底有效占用冲突。
3. 抢票链路已经具备 `Redis Lua + MQ + worker + DB 硬兜底 + 用户唯一约束` 的基本架构意识。
4. 订单状态迁移用了 `version + updateMany` 做 CAS，并保留状态日志，说明一致性问题被认真考虑过。
5. judge 一键启动、Nginx 统一入口、README 与 smoke 路径都比较适合比赛现场演示。

## E. 最可能在答辩或演示中被追问的 10 个问题

1. 你们的 `PENDING_CONFIRMATION` 订单在哪条正式业务链路里真实产生？
2. 支付成功回调晚于超时取消时，你们如何处理幽灵支付？
3. `PaymentRecord` 目前只是建模，还是已经参与主流程？
4. 活动 `totalQuota` 和票种 `stock` 发生冲突时，以哪个为准？
5. 为什么你们认为当前 Redis 补偿策略不会把热点重新打回数据库？
6. Redis 库存和数据库库存不一致时，系统如何自愈？
7. 新增一个全新的业务规则类型时，是否必须改后端代码？
8. 你们如何证明前端满足 WCAG 2.2？
9. 你们如何证明前端满足 Core Web Vitals？
10. 你们为什么没有把预约冲突、抢票、签到、取消等核心流程纳入自动化测试？
