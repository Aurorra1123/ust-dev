# 管理员前端重组方案（2026-04-21）

## 1. 文档目的

- 将管理员端新的信息架构调整正式固化下来，避免后续继续围绕旧的“资源 / 规则 / 活动”技术视角反复讨论。
- 明确这次改造的边界：本轮只重构管理员前端的信息架构与页面组织，不主动扩展后端模型、接口协议和数据库 Schema。
- 为后续开发拆分、验收、汇报和回归提供统一入口。

## 2. 当前现状

### 2.1 代码中的当前管理员结构

当前管理员入口位于 `apps/web/src/ui/pages/admin/index.tsx`，一级工作区仍然是：

- `overview`
- `resources`
- `activities`
- `rules`
- `notifications`
- `serviceRequests`

对应标签定义位于 `apps/web/src/ui/pages/admin/admin-helpers.ts`。

### 2.2 当前结构存在的问题

当前后台的信息架构仍然偏“系统实现视角”，而不是“管理员业务视角”：

1. “资源工作区”把学术空间和体育设施混在一起，管理员需要先理解技术上的资源类型，再去找自己真正要管理的业务对象。
2. “规则工作区”作为独立一级模块暴露过强，但它本质上是低频、技术性较强的后台能力，不适合作为当前演示版后台主路径。
3. 学术空间和体育设施虽然共用同一套资源接口，但在管理员认知里是两条完全不同的业务线：
   - 体育场馆更接近“篮球场 / 羽毛球场 / 网球场”这样的场馆对象管理
   - 学术空间更接近“E1 / E2 / E3 / E4 区域下的房间与自习空间”管理
4. 当前后台模块名称与用户测试中管理员的真实语言不一致，容易造成“代码里是合理的，现场却不好解释”的落差。

## 3. 本轮目标与边界

### 3.1 目标

本轮目标是把管理员端前端入口重组为以下 6 个业务模块：

- 运营总揽
- 体育场馆
- 学术空间
- 活动管理
- 工单维修
- 通知发布

### 3.2 明确边界

本轮明确只做以下类型的调整：

- 管理员端一级导航和模块命名调整
- 原“资源工作区”的拆分与重组
- 学术空间按区域索引组织
- 规则工作区入口下线
- 保留既有活动、工单、通知页面逻辑

本轮明确不做以下事情：

- 不新增后端接口
- 不修改数据库 Schema
- 不删除规则引擎后端能力
- 不重做活动管理页面
- 不重做工单维修页面
- 不重做通知发布页面

## 4. 目标信息架构

### 4.1 一级模块

| 目标模块 | 说明 | 当前来源 |
| --- | --- | --- |
| 运营总揽 | 展示今日需要关注的运营信息与快捷入口 | 保留现有 `overview`，调整跳转目标 |
| 体育场馆 | 管理篮球场、羽毛球场、网球场等体育资源 | 从 `resources` 拆分 |
| 学术空间 | 按 `E1 / E2 / E3 / E4 ...` 组织与管理学术空间 | 从 `resources` 拆分 |
| 活动管理 | 管理活动与票种 | 直接复用现有 `activities` |
| 工单维修 | 管理报修工单与状态流转 | 直接复用现有 `serviceRequests` |
| 通知发布 | 管理通知草稿与发布 | 直接复用现有 `notifications` |

### 4.2 旧模块到新模块的映射

| 当前模块 | 目标处理方式 |
| --- | --- |
| 运营总览 | 保留，但调整快捷跳转入口 |
| 资源工作区 | 拆成“体育场馆”和“学术空间”两个独立模块 |
| 活动工作区 | 保留并重命名为“活动管理” |
| 规则工作区 | 从一级导航下线，不再作为管理员主路径入口 |
| 通知工作区 | 保留并重命名为“通知发布” |
| 工单工作区 | 保留并重命名为“工单维修” |

## 5. 各模块职责设计

### 5.1 运营总揽

运营总揽继续承担“后台首页”的角色，但职责要更清楚：

- 只展示总览信息和快速入口
- 不继续承担复杂写操作
- 快捷入口需要改为跳向新的 5 个业务模块，而不是旧的 `resources / rules` 结构

本轮不重做运营总揽的数据来源，只调整它的模块命名和跳转语义。

### 5.2 体育场馆

体育场馆模块面向管理员管理体育预约资源，重点对象包括：

- 篮球场
- 羽毛球场
- 网球场
- 其他体育设施

#### 目标页面职责

- 只展示 `sports_facility` 类型资源
- 管理体育资源的基础信息
- 管理体育资源单元，例如具体场地
- 查看当前预约状态与时间窗口内的占用情况
- 管理预约关闭规则与高级调度设置

#### 页面组织建议

- 左侧：体育资源列表，只显示体育类资源
- 中间：当前选中场馆的概况、资源单元、关闭规则、预约状态
- 右侧：新增体育资源、新增资源单元、关闭规则配置、开放策略配置

#### 设计原则

- 管理员不需要先理解“资源类型切换”，进入模块后默认就是体育场馆上下文
- “篮球场 / 羽毛球场 / 网球场”通过资源列表直接切换，不再和学术空间资源混排
- 现有“资源工作区”里已经存在的资源操作逻辑尽量复用，不做二次发明

### 5.3 学术空间

学术空间模块面向管理员管理自习室、研讨室、创新协作室等学术资源。

#### 目标页面职责

- 只展示 `academic_space` 类型资源
- 按 `E1 / E2 / E3 / E4 ...` 组织资源
- 管理学术空间的基础信息和资源单元
- 查看当前预约状态与连续时间视图相关信息
- 管理预约关闭规则与高级调度设置

#### 区域组织规则

用户已经明确接受按 `E1 / E2 / E3 / E4 ...` 来组织学术空间。本轮默认采用以下规则：

1. 优先从资源 `code` 前缀中提取区域索引。
2. 若 `code` 以 `E1`、`E2`、`E3`、`E4` 等模式开头，则归入对应区域。
3. 若资源没有符合规则的前缀，则进入“未分区”或等价兜底分组。

采用 `code` 前缀而不是 `location` 的原因是：

- 规则更稳定
- 与后台运营输入更容易保持一致
- 无需引入新的数据字段

#### 页面组织建议

- 顶部或左侧增加区域切换，例如 `E1 / E2 / E3 / E4 / 未分区`
- 资源列表只展示当前区域下的学术空间
- 当前资源详情区继续保留资源单元、关闭规则、预约状态等核心管理能力

### 5.4 活动管理

活动管理本轮不改实现，只改后台模块命名和导航位置。

保留原则：

- 保留当前活动创建与票种追加逻辑
- 保留已完成的“默认首票 + 进阶设置折叠”结构
- 不在本轮把活动页和资源页的体验问题混在一起处理

### 5.5 工单维修

工单维修本轮不改实现，只做命名与导航归位。

保留原则：

- 保留当前工单列表、状态变更、管理员备注等逻辑
- 只把模块名称从“工单工作区”收口为更贴近业务表达的“工单维修”

### 5.6 通知发布

通知发布本轮不改实现，只做命名与导航归位。

保留原则：

- 保留当前通知列表、草稿、发布与更新能力
- 不在本轮引入新的通知类型或发布流程

### 5.7 规则工作区的处理

规则工作区本轮从管理员一级导航中下线，但这不等于删除规则系统。

本轮产品结论如下：

1. 后端规则引擎、规则模型和已有接口继续保留。
2. 前端一级导航不再暴露“规则工作区”。
3. 当前阶段不再把“规则管理”作为管理员的主操作路径。
4. 若未来需要恢复规则可视化运营能力，应重新按“附属能力”而不是“一级主模块”的方式设计入口。

这样处理的原因是：

- 它与当前管理员最核心的日常任务不匹配
- 解释成本高
- 会继续把后台导航拉回“技术实现导向”

## 6. 技术落地方案

### 6.1 总体策略

本轮采用“前端重组、后端复用”的落地方式：

- 保留现有 `admin/resources` 查询与写接口
- 保留现有 `activities / notifications / serviceRequests` 的前端工作区实现
- 只在管理员前端对资源工作区做类型拆分与壳层重构

### 6.2 建议的前端重构路径

#### 步骤 1：重构管理员标签与模块映射

- 调整 `WorkspaceTab` 定义
- 将旧的 `resources` 替换为：
  - `sportsVenues`
  - `academicSpaces`
- 删除 `rules`
- 保留：
  - `overview`
  - `activities`
  - `notifications`
  - `serviceRequests`

#### 步骤 2：将现有资源工作区抽成共享基础能力

当前 `ResourcesWorkspace` 已经包含很多成熟逻辑：

- 资源查询
- 资源单元创建
- 关闭规则创建
- 开放策略创建
- 预约状态查看
- 管理员取消预约

本轮不建议复制一份大页面，而是建议把它拆成：

- 一个共享的资源域工作区基础组件
- 两个壳层页面：
  - `SportsVenuesWorkspace`
  - `AcademicSpacesWorkspace`

两个壳层只负责：

- 资源类型过滤
- 页面标题、说明和默认表单文案
- 学术空间区域分组逻辑

共享基础组件继续复用已有 mutation、query 和状态展示逻辑。

#### 步骤 3：实现体育场馆专属上下文

体育场馆页需要：

- 仅加载或仅展示 `sports_facility`
- 默认创建资源时预设为体育设施
- 资源单元默认类型保持体育场地语义
- 中英文文案从“资源工作区”改为“体育场馆”

#### 步骤 4：实现学术空间专属上下文

学术空间页需要：

- 仅加载或仅展示 `academic_space`
- 默认创建资源时预设为学术空间
- 资源单元默认类型保持房间语义
- 根据 `code` 前缀生成区域分组
- 为没有合法前缀的资源提供兜底分组

#### 步骤 5：移除规则工作区入口

- `AdminPage` 中不再渲染 `RulesWorkspace`
- 总览页的快捷入口同步删除规则入口
- 后台一级导航与文案说明同步更新

### 6.3 为什么本轮不改后端

这次改造的核心问题是“管理员看到的页面组织不符合业务心智”，而不是“接口不够用”。当前后端接口已经足够支撑两类资源页面，只是前端把它们错误地揉进了一个过宽的工作区。

如果这一轮同时改前端信息架构和后端领域边界，会引入不必要的联动风险：

- 查询键可能大面积变化
- 写操作回归面会变宽
- 容易把“结构改造”拖成“系统重构”

因此本轮最合理的策略是：

- 先让管理员端结构对齐业务认知
- 再看是否有必要在后续继续向后端抽更细的领域服务

## 7. 与现有待办的关系

### 7.1 本轮直接覆盖的体验问题

本方案会直接改善以下问题：

- 管理员后台模块命名与真实业务语言不一致
- 学术空间与体育资源混排
- 规则工作区作为一级入口的干扰感

### 7.2 本轮不直接解决但不能丢失的问题

以下问题仍然保留在开发列表中，不能因为导航重组而消失：

- `UTG-011`：学术空间零单元资源导致学生端时间轴空白
- `UTG-012`：管理员无法撤销预约关闭规则

另外，当前管理员反馈中这些问题会被本轮部分改善，但不应误判为已自动解决：

- 表单提示不足
- 活动创建页字段说明不足
- 中英业务内容不同步

## 8. 分阶段实施计划

### 阶段 A：方案固化与任务拆分

- 新增正式方案文档
- 新增 ADR
- 将开发列表拆成 `ADM-*` 任务

### 阶段 B：管理员入口重组

- 改管理员一级标签
- 调整总览快捷入口
- 下线规则工作区主入口

### 阶段 C：体育场馆工作区落地

- 从资源工作区拆出体育场馆页
- 保持现有写操作和查询逻辑可用
- 回归校验创建资源、创建资源单元、关闭规则、查看预约状态

### 阶段 D：学术空间工作区落地

- 从资源工作区拆出学术空间页
- 接入区域索引分组
- 回归校验创建资源、创建资源单元、关闭规则、查看预约状态

### 阶段 E：收尾与回归

- 清理旧文案和旧入口
- 校验中英文模式下的新导航和页面标题
- 记录验证证据

## 9. 风险与约束

### 9.1 学术空间分组依赖命名规范

按 `code` 前缀分组的前提是资源编码本身具备一致性。如果实际数据里存在大量不规范编码，就会出现较多“未分区”资源。

应对方式：

- 本轮先接受“未分区”兜底
- 后续如需要，再补资源编码规范或后台校验

### 9.2 不能把资源工作区简单复制成两份

当前 `ResourcesWorkspace` 已经很大。如果直接复制两份，会快速制造新的代码重复和后续维护成本。

应对方式：

- 优先抽共享基础组件
- 由两个业务模块做壳层包装

### 9.3 规则能力仍然存在但前端主入口消失

这会带来一个预期管理问题：系统依然有规则引擎，但管理员在新版后台看不到一级入口。

应对方式：

- 在 ADR 中明确这是“下线主入口”，不是“删除能力”
- 后续如真要恢复规则运营入口，需要单独重新设计，不直接恢复旧页

## 10. 验收标准

本方案落地后，应满足以下标准：

1. 管理员后台一级模块变为：
   - 运营总揽
   - 体育场馆
   - 学术空间
   - 活动管理
   - 工单维修
   - 通知发布
2. 后台主导航中不再出现“资源工作区”和“规则工作区”。
3. 体育场馆页只管理体育设施，不再混入学术空间资源。
4. 学术空间页只管理学术资源，并能按 `E1 / E2 / E3 / E4 ...` 组织展示。
5. 活动管理、工单维修、通知发布三块能力在重组后保持可用，不因导航改造发生回退。
6. 本轮不引入新的后端接口、不修改数据库 Schema。

## 11. 非目标

以下事项明确不属于本方案的直接交付：

- 活动管理表单的进一步精简
- 关闭规则撤销能力的实现
- 业务数据正文的真正双语化
- 规则系统的后端移除或重设计

这些事项需要保留在独立任务中推进，而不是混入本次管理员信息架构重组。
