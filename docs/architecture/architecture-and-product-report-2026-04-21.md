# CampusBook 架构与产品使用报告（中文初稿）

## 一、报告摘要

`CampusBook（智约校园）` 是一个面向校园场景的统一预约与活动平台，目标是把原本分散的空间预约、体育设施预订和热门活动报名整合到同一套产品与技术体系中。

从当前代码实现来看，系统已经形成了三条真实可用的核心业务链路：

- 学术空间预约
- 体育设施预约
- 校园活动报名与高并发抢票

系统当前采用单机容器化部署架构，由 `Web 前端 + API 服务 + Worker 异步任务服务 + PostgreSQL + Redis + Nginx` 组成。产品层面，它已经提供学生端预约使用流程和管理员工作台；技术层面，它已经落地了多态空间建模、活动抢票防超卖、统一订单状态管理、规则引擎和异步任务处理等关键能力。

需要特别说明的是，本报告以当前仓库中的真实代码为依据撰写，因此会严格区分“已经实现的能力”和“仍处于基础设施预留或后续优化阶段的能力”。例如，系统当前已经具备统一订单状态机骨架，但预约与活动报名主链路目前大多直接进入 `CONFIRMED`，真实支付闭环和完整的“幽灵支付”对撞流程仍有待补齐。

## 二、项目背景与产品目标

在校园日常生活中，学生经常会遇到三个典型问题。

第一，预约入口分散。空教室、讨论室、体育场地和校园活动往往来自不同系统，信息不统一，操作习惯也不一致。  
第二，规则复杂。不同资源的时间规则、释放规则、关闭规则、冲突规则都不一样，如果系统设计不合理，很容易在业务增长后变得难以维护。  
第三，高峰期容易失稳。尤其是热门活动抢票，如果所有请求直接落到数据库，就很容易出现超卖、排队失控或者系统响应变慢。

因此，`CampusBook` 的目标并不是简单做一个“预约页面集合”，而是要建设一套兼顾产品体验和系统稳健性的校园服务平台。它在产品上追求统一入口和清晰流程，在技术上追求以下四个核心目标：

1. 用统一的领域模型表达不同类型的校园资源。
2. 用可靠的冲突控制机制保证预约数据正确。
3. 用异步和缓存机制支撑活动抢票等热点并发场景。
4. 用统一订单体系串联预约、报名、签到、取消和缺席处理等后续流程。

## 三、产品使用说明

### 3.1 用户角色

当前系统中有两类正式角色：

- `STUDENT`：普通学生用户，可以登录、浏览资源、发起预约、报名活动、查看和取消自己的订单。
- `ADMIN`：管理员用户，可以进入教师工作台，对资源、活动和规则进行维护。

目前系统没有开放式注册流程，登录主要依赖演示账号和系统中已有的用户数据。这意味着它已经适合演示和答辩场景，但如果未来进入正式运行，还需要补完整的身份接入与注册/导入机制。

### 3.2 学生端使用流程

学生登录后会进入首页，首页提供三类主入口：

- 学术空间
- 体育设施
- 校园活动

此外，学生还可以从首页直接进入“我的订单”，统一查看自己所有预约和报名的结果。

#### 1. 学术空间预约

在学术空间页面，用户首先选择具体的资源单元，例如某一间讨论室或会议室，然后输入开始时间和结束时间，必要时还可以填写同行人邮箱。提交后，系统会自动完成以下判断：

- 当前资源是否处于可预约状态
- 当前时段是否落在资源的开放通道内
- 是否命中闭馆或封禁时间
- 当前用户是否满足绑定在该资源上的规则
- 该时间段是否与已有预约发生冲突

如果校验全部通过，系统会立即生成订单并返回订单详情页。当前实现中，学术预约成功后会直接进入“已确认”状态。

#### 2. 体育设施预约

体育设施页面和学术空间页面的最大差异，在于它不是连续时间段预约，而是基于离散的 `1` 小时槽位来进行预订。

用户可以选择：

- 单个场地单元预约
- 多个场地组成的组合预约

页面会先读取指定时间窗口内的公开占用状态，帮助用户理解哪些槽位可选。用户选择目标场地和槽位后，系统会检查：

- 目标资源是否属于体育设施
- 目标资源单元是否支持离散槽位模式
- 所有被选中的槽位是否全部可用
- 是否存在组合预约中的任意单元冲突

只要组合中的任意一个场地单元、任意一个目标槽位发生冲突，整单就会失败。这个设计符合体育比赛或联动场地场景的实际业务逻辑。

#### 3. 校园活动报名与抢票

活动页提供活动列表、活动详情和票种选择能力。与普通预约不同，活动报名不是同步“立即建单”，而是分为两个阶段：

第一阶段是前台请求受理。用户点击报名后，系统会先快速判断活动是否可报名、票种是否有效、用户是否已报名。  
第二阶段是后台异步建单。前端收到“已排队”结果后，会周期性轮询报名状态；Worker 再异步完成最终库存确认和订单写入。

这个设计的好处是，面对抢票高峰时，系统不需要让所有用户请求都同时等待数据库事务完成，而是先把请求压到更适合承接瞬时流量的缓存和队列层，再由后台平稳消费。

#### 4. 我的订单与订单详情

系统把学术预约、体育预约和活动报名统一收敛到同一套订单中心中。用户可以在订单列表查看：

- 订单类别
- 预约资源
- 创建时间
- 当前状态

进入订单详情后，用户还可以根据订单类型执行进一步操作。例如资源预约类订单支持签到，部分订单在允许条件下还支持取消。

### 3.3 管理端使用流程

管理员登录后会自动进入 `/admin` 对应的教师工作台。当前工作台按“工作区”组织，而不是把所有表单和表格堆在一个超长页面里。

当前主要包含三个核心工作区：

- 资源工作区：维护资源、资源单元、组合资源、发布规则、闭馆规则
- 活动工作区：维护活动、票种和发布状态
- 规则工作区：维护规则定义并绑定到具体资源

这种分区方式对后续扩展是有利的，因为它把“资源管理”“活动管理”“规则管理”三类关注点分开了，避免后台逐渐演化成难以维护的巨型页面。

## 四、系统总体架构设计

### 4.1 架构概览

当前系统采用单机容器化架构，核心组件如下：

- `Web`：React 单页应用，负责学生端和管理端界面
- `API`：NestJS 服务，负责鉴权、资源读取、预约创建、活动抢票入口、订单查询与状态迁移
- `Worker`：独立运行的 BullMQ 消费者，负责活动报名异步建单、预约签到缺席判定、订单超时取消等后台任务
- `PostgreSQL`：关系型数据库，保存最终一致性数据
- `Redis`：承接热点库存、排队状态和 BullMQ 队列
- `Nginx`：负责域名分流、静态文件托管与 API 反向代理

这套架构的一个关键优点，是把“同步响应用户请求”的工作和“异步处理后台任务”的工作拆开了。这样一来，前台接口可以保持更轻、更快，后台复杂逻辑则交给 Worker 在更可控的节奏下处理。

### 4.2 前后端协作方式

前端通过 `Authorization: Bearer <access_token>` 调用业务接口，同时通过 `HttpOnly refresh token Cookie` 保持会话续期能力。  
API 服务对外暴露统一的 HTTP 接口，并将需要异步处理的任务写入 Redis/BullMQ 队列。  
Worker 进程则订阅这些队列，在后台执行建单、状态修正和缺席处理。

这意味着系统并不是“前端直接连数据库”，也不是“所有逻辑都在同一个 Node 进程里做完”，而是已经具备了比较清晰的分层边界。

## 五、多态空间数据库 Schema 设计

### 5.1 为什么需要“多态空间”设计

校园资源看起来都叫“预约”，但本质差异非常大。

学术空间更像“一个不可分割的原子资源”，适合连续时间段预约。  
体育设施则更像“多个场地单元的集合”，适合按固定槽位离散预约，还可能涉及组合场地。  
如果把这两类资源强行塞进同一张扁平表里，短期似乎省事，长期就会出现大量条件判断、字段语义混乱、扩展困难等问题。

因此，当前代码采用了“资源主实体 + 原子单元 + 组合资源 + 业务占用表”的多层建模方式。

### 5.2 主要数据实体

#### 1. `Resource`

`Resource` 是资源聚合根，用来表达“一个校园资源类别或资源主体”。它通过 `type` 区分：

- `ACADEMIC_SPACE`
- `SPORTS_FACILITY`

也就是说，`Resource` 不是具体某一条预约记录，而是“某类可被预约资源”的主实体。

#### 2. `ResourceUnit`

`ResourceUnit` 表示可直接被占用的最小资源单元。例如：

- 一间具体讨论室
- 一个具体球场
- 某个体育场馆中的单个分区

这样设计的好处是，不管是学术空间还是体育设施，最终都可以落回“占用了哪些具体单元”这一层面来处理。

#### 3. `ResourceGroup` 与 `ResourceGroupItem`

体育设施的难点在于，用户有时不是预约一个场地，而是预约“一组场地”。例如一场比赛可能需要两个相邻场地同时可用。

为了解决这个问题，系统引入了：

- `ResourceGroup`
- `ResourceGroupItem`

`ResourceGroup` 负责表示一个组合资源，`ResourceGroupItem` 则负责把组合资源和具体 `ResourceUnit` 连接起来。这使得“组合预约”可以成为数据库中的正式结构，而不是只在前端页面里临时拼接出来的概念。

### 5.3 业务占用表的拆分

#### 1. `AcademicReservation`

学术空间采用独立的 `AcademicReservation` 表，主要记录：

- 对应订单
- 用户
- 资源与资源单元
- 展示用开始时间和结束时间
- 前后缓冲分钟数
- 当前状态

看似这里只保存了用户真正选择的开始和结束时间，但数据库约束并不只看这两个时间点，而是会把前后缓冲一起算进去。这使系统既能对用户保持简单的预约界面，又能在底层严谨拦截重叠冲突。

#### 2. `SportsReservationSlot`

体育设施采用 `SportsReservationSlot` 表，明确记录每个离散槽位的占用情况。  
也就是说，一次体育预约如果包含 `3` 个时段、`2` 个场地单元，那么数据库里最终会有多条槽位记录，而不是一条含糊的大区间记录。

这种设计虽然表面上记录数更多，但它带来了非常重要的好处：数据库可以直接对 `(resourceUnitId, slotStart)` 建立唯一约束，从结构层面保证“同一场地在同一时间只能被一张有效订单占用”。

### 5.4 统一订单如何与多态空间配合

为了让不同业务最终都能归到统一的订单中心，系统又引入了：

- `Order`
- `OrderItem`

`Order` 负责承载统一状态、用户、业务类型、金额等公共信息。  
`OrderItem` 负责承载订单明细，可以指向：

- 学术空间相关的资源与时间
- 体育设施相关的资源单元与槽位
- 活动报名相关的票种

这样做的价值在于，系统既没有牺牲不同业务类型的专业建模能力，又保留了统一订单视角，便于后续在产品层面集中展示。

## 六、高并发防超卖策略

### 6.1 问题本质

热门活动抢票最大的风险，不是“页面不好看”，而是并发时系统很容易把库存卖超。

如果所有用户在同一秒内都直接操作数据库，一方面数据库压力会迅速升高，另一方面即使加锁，也容易在吞吐和一致性之间陷入两难。  
因此，活动抢票必须把“瞬时高并发入口”和“最终一致性写库”拆开处理。

### 6.2 当前系统采用的四层保护

#### 第一层：入口资格校验

在请求刚进入 API 时，系统会先检查：

- 用户是否有效
- 活动是否已发布
- 当前时间是否处于售卖窗口
- 指定票种是否可报名
- 用户是否已经存在有效报名

这一步的目的是尽量在进入并发核心链路之前就过滤掉无效请求。

#### 第二层：Redis 预扣与判重

通过资格校验后，系统不会立即进入数据库，而是先进入 Redis。

当前代码中，Redis 层完成三件事：

1. 判断该用户是否已有 pending 报名请求  
2. 判断票种剩余库存是否还大于 `0`  
3. 若可继续，则先执行一次预扣，把剩余库存减 `1`

这一步使用的是 Lua 脚本完成原子操作，因此不会出现“刚判断还有库存，下一行代码就被别人抢完了”的中间态问题。

#### 第三层：BullMQ 异步排队

预扣成功后，API 不会同步等待数据库建单完成，而是立即把任务写入 BullMQ 队列，并返回前端“已排队”的结果。

这一步非常关键，因为它把高峰期的“瞬时请求洪峰”转换成了后台可平稳消费的任务流。对用户来说，请求响应更快；对系统来说，也避免了高峰期同步事务过多导致的抖动。

#### 第四层：数据库最终库存兜底

Worker 在后台消费任务时，会再次进行数据库层面的最终校验。当前代码没有简单地“相信 Redis 的结果”，而是执行了一条带条件的原子更新：

- 只有在 `reserved < stock` 时，才允许把 `reserved` 加 `1`

如果这一步失败，说明即使前面 Redis 曾经预扣成功，数据库层依然认为库存已经无法再确认，此时系统会：

- 回补 Redis 的 pending 预扣
- 记录失败原因
- 返回失败状态

这说明当前系统的库存正确性最终是由数据库守住的，而 Redis 主要负责承接流量和加速判定。

### 6.3 为什么这种策略更稳

这套策略的核心思想可以概括为一句话：

“先用 Redis 快速承接流量，再用队列削峰，最后由数据库做最终一致性确认。”

这样做不是为了堆技术栈，而是为了同时满足三件事：

- 高峰时不要把数据库打垮
- 不要让用户长时间阻塞等待
- 无论并发多大，都不能超卖

从当前实现看，这部分已经是系统中完成度最高、也最接近比赛核心考点的技术链路之一。

## 七、状态机流转设计

### 7.1 为什么要统一订单状态机

如果学术预约、体育预约和活动报名各自维护一套完全不同的状态，不仅前端难展示，后端也很难保证行为一致。  
因此，系统引入统一订单状态机，把不同业务最终都收敛到同样的状态语言上。

当前订单状态包括：

- `PENDING_CONFIRMATION`
- `CONFIRMED`
- `CANCELLED`
- `NO_SHOW`

### 7.2 当前代码中的真实状态流转

从代码实现来看，状态机骨架是完整的，支持：

- 从 `PENDING_CONFIRMATION` 到 `CONFIRMED`
- 从 `PENDING_CONFIRMATION` 到 `CANCELLED`
- 从 `CONFIRMED` 到 `CANCELLED`
- 从 `CONFIRMED` 到 `NO_SHOW`

并且所有状态迁移都不是简单 `update status`，而是通过以下方式完成：

- 先读取当前订单状态与版本号
- 基于 `version + status` 做 CAS 更新
- 写入 `OrderStatusLog`
- 同步更新子表状态

这意味着系统在设计上已经考虑到并发状态覆盖问题，而不是允许后到请求直接把先到请求的结果冲掉。

### 7.3 当前实现与理想终态的差异

虽然状态机结构完整，但当前主创建链路存在一个很重要的现实情况：

- 学术预约创建成功后直接进入 `CONFIRMED`
- 体育预约创建成功后直接进入 `CONFIRMED`
- 活动报名 Worker 建单成功后直接进入 `CONFIRMED`

也就是说，`PENDING_CONFIRMATION` 在当前代码中更像“已预留但尚未被主链路使用的能力”，而不是正在广泛运行的真实主状态。

这也带来两个直接影响：

第一，管理员确认接口和超时取消 Worker 虽然都存在，但当前很少真正被主流程触发。  
第二，支付成功和超时取消同时发生时的“幽灵支付”问题，当前还没有完整的真实支付场景来验证。

### 7.4 签到与缺席判定

当前系统比传统状态机更进一步的一点，是它已经把预约后的到场行为也纳入了状态管理。

对于资源预约类订单，系统定义了签到窗口：

- 预约开始前 `10` 分钟
- 到预约开始后 `10` 分钟

如果在这个窗口内，没有任何参与人完成签到，后台 Worker 会把订单自动转成 `NO_SHOW`，并对相关用户累计违规次数。  
当违规达到一定次数后，系统还会对该用户在特定预约类别上的后续使用进行限制。

这说明当前状态机已经不仅在处理“下单与取消”，也开始承载“履约与信用管理”的职责。

## 八、无障碍与性能优化实践

这一部分需要特别严谨地说明：当前系统已经具备一些良好的工程基础，但如果按比赛题面对 `WCAG 2.2` 和 `Core Web Vitals` 的高标准来衡量，仍然属于“已开始实践、仍需持续加强”的状态。

### 8.1 当前已经具备的基础

#### 1. 清晰的页面分工与路由守卫

当前前端已经将学生端和管理端主路径分开，并通过路由守卫控制访问权限。  
这对于可用性和可理解性很重要，因为用户不会轻易误入与自己角色不匹配的页面。

#### 2. 统一的 API 调用层与会话恢复机制

前端已经封装统一的 HTTP 客户端，支持：

- Access Token 自动携带
- `401` 后自动尝试刷新会话
- 统一错误处理

这类设计虽然主要属于工程优化，但对用户体验有直接帮助，因为它减少了“页面忽然失效”或“登录态莫名丢失”的情况。

#### 3. 静态前端与 API 分域部署

系统通过：

- `campusbook.top / www.campusbook.top`
- `api.campusbook.top`

进行前后端分域，静态资源由 Nginx 托管。这种方式通常有助于前端资源缓存、反向代理优化和整体响应稳定性。

#### 4. 页面结构已经较为明确

从当前前端实现来看，学生端主页面已经不再是杂乱的原型拼接，而是围绕预约、活动、订单等核心任务组织。  
这对于“可理解”和“可操作”两个无障碍维度是有帮助的。

### 8.2 当前仍需继续加强的部分

#### 1. 无障碍证据还不够充分

比赛题面明确要求：

- 图片需要有替代文本
- 表单需要明确标签
- 色彩对比度应达标
- 核心流程需要可键盘操作

从当前代码可见，页面已经在使用较规范的表单结构和基础语义标签，但是否系统性达到 `WCAG 2.2` 水平，还需要进一步做专项检查和留证。  
换句话说，当前可以说“已有无障碍意识和基础实现”，但还不适合直接宣称“已完整通过 WCAG 2.2 规范验收”。

#### 2. 性能指标已有工程基础，但缺少实测报告

当前架构有利于性能优化：

- 静态前端由 Nginx 托管
- API 与页面分离
- 抢票场景异步化
- 查询与写入边界较清晰

但如果要对应题面中的：

- `LCP <= 2.5s`
- `INP <= 200ms`
- `CLS <= 0.1`

仍需要补充 Lighthouse、Web Vitals 或真实浏览器采样数据。  
因此更准确的表述应该是：系统已经具备支持性能优化的工程基础，但还需要补齐可量化的性能验证证据。

### 8.3 适合在正式报告中的表述方式

如果这份报告用于提交或答辩，建议使用更严谨的表达：

- 不要写“已经完全满足所有无障碍和性能指标”
- 而应写“当前已完成基础结构建设，并围绕可访问性与性能建立了可持续优化的工程基础”

这种说法既不虚夸，也能体现团队对质量标准的重视。

## 九、当前系统的优势与后续改进方向

### 9.1 当前优势

结合现有代码，系统目前最值得强调的优势主要有四点。

第一，多态空间建模合理。  
它没有把学术空间和体育设施粗暴塞进一张通用预约表，而是通过 `Resource / ResourceUnit / ResourceGroup / AcademicReservation / SportsReservationSlot` 建立了清晰、可扩展的数据边界。

第二，高并发抢票链路真实落地。  
系统已经不是“以后可以接 Redis 和队列”，而是已经实际使用 `Redis Lua + BullMQ + Worker + PostgreSQL` 承接抢票场景。

第三，统一订单中心已经成型。  
无论是预约还是活动报名，用户最终都能在同一套订单体系里查看结果，这对产品统一性很重要。

第四，异步与后置治理能力已经开始发挥作用。  
签到、缺席判定、违规限制等逻辑说明系统已经超出“能下单就算完成”的阶段，开始真正考虑校园场景中的长期治理问题。

### 9.2 当前最需要继续补强的方向

如果以比赛最终答辩为目标，接下来最重要的补强点有三类。

#### 1. 支付与待确认链路

当前最大短板是，虽然状态机和 `PaymentRecord` 模型都在，但系统还没有形成真实支付闭环。  
这意味着：

- `PENDING_CONFIRMATION` 尚未成为主链路状态
- `expireAt` 尚未在建单时被真正使用
- “幽灵支付”仍缺乏完整演示场景

#### 2. 规则引擎覆盖面

当前规则引擎已经可用，但范围仍集中在预约前置校验。  
如果继续增强，可以让规则系统接管：

- 更多用户身份差异
- 信用分扣减与恢复
- 爽约惩罚
- 活动资格限制

#### 3. 质量验证证据

从答辩角度看，后续除了补功能，更要补“证据”。  
特别是：

- 无障碍专项检查结果
- 页面性能实测数据
- 并发压测结果
- 极端边界场景验证记录

这些内容会显著提高报告和演示的说服力。

## 十、结语

总体来看，`CampusBook` 当前已经不是一个停留在概念层面的作品，而是一套具备真实产品路径和真实工程结构的校园服务系统。

它在产品层面，已经形成了“统一入口、统一订单、前后台分工清晰”的基本体验；  
它在技术层面，已经完成了多态空间建模、活动抢票异步化、数据库冲突保护、规则引擎接入和 Worker 分离等关键设计；  
它在系统治理层面，也已经开始考虑签到、缺席、限制和异步补偿等更贴近真实校园场景的问题。

同时，本项目也保留了足够清醒的边界意识：当前并没有把未落地的支付闭环、完整待确认链路和全面质量验收包装成既成事实，而是把它们明确识别为下一阶段需要继续完成的工作。

这正是一个面向真实交付的系统应有的状态：既有已经落地的核心能力，也有清晰明确的下一步演进路线。
