# 比赛演示视频闭环脚本方案（浏览器主视频版，2026-04-22）

## 1. 文档目的

- 将比赛主视频方案收口为“纯浏览器录屏版”。
- 主视频只录制从域名打开的网站，不出现终端、仓库文件、CI 页面或本地脚本执行过程。
- 只保留评委能在浏览器画面里直接理解的核心业务闭环。
- 对于不适合在浏览器里展开的工程与一致性能力，单独标记为 README、答辩口头补充和附件材料。

## 2. 主视频边界

本方案明确采用以下边界：

1. 主视频只在浏览器中完成。
2. 允许展示：
   - 学生端页面
   - 管理端 `/admin` 工作台
3. 不在主视频中展示：
   - `README`
   - `judge-up`
   - `docker-compose`
   - `CI`
   - 自动化测试执行
   - 架构图
   - verification 文档
   - 终端日志
4. 这些内容仍然重要，但属于：
   - 提交材料
   - README
   - 架构文档
   - 答辩补充

## 3. 当前判断

结论：当前仓库最适合做“浏览器里的业务闭环演示”，而不是“网站页面巡礼”。

原因：

1. 比赛高分点并不在于页面多，而在于：
   - 学术空间与体育设施采用不同底层调度模型
   - 活动报名不是同步下单，而是排队后进入状态机
   - 规则限制、冲突拦截、支付确认、取消回写都能在浏览器中看到结果
2. 浏览器镜头里最有价值的不是“首页长什么样”，而是：
   - 正常创建
   - 冲突/非法输入被拦截
   - 规则限制生效
   - 状态变化与后续动作
3. 管理端 `/admin` 也是同域名下的一部分，因此可以承担“这些限制和配置不是写死的”这一证明任务。

## 4. 主视频总体策略

主视频采用四段式浏览器闭环：

1. 学术空间闭环
   - 连续时间
   - `5` 分钟缓冲
   - 时长规则
   - 取消订单
2. 体育设施闭环
   - `1` 小时 slot
   - 组合资源
   - 成功后整组占用
3. 活动报名支付闭环
   - `queued`
   - `pending_confirmation`
   - `Mock Pay`
   - `confirmed`
4. 管理端规则中心收口
   - 说明前面的限制来自后台工作台配置
   - 不在主视频里展开工程细节

这套顺序优先争取：

- `A. 系统架构与领域建模`
- `B. 高并发与状态机处理`
- `D. 动态规则与代码质量`
- `F. 创新性与展示表达`

`C. 产品体验与 Web 标准` 通过轻量浏览器细节补充：

- `skip link`
- 焦点可见
- 响应式浏览器缩放或窄宽度视图

`E. DevOps 与自动化验收` 不放入主视频主体，改为材料与答辩补充。

## 5. 主视频适合展示的功能链清单

### 5.1 学术空间预约闭环链

- 涉及页面：
  - 首页 `/`
  - 学术空间 `/spaces`
  - 我的订单 `/orders`
  - 订单详情 `/orders/:orderId`
- 建议动作：
  1. 从首页进入学生端
  2. 打开学术空间页
  3. 先输入超过 `120` 分钟的时间段，触发时长规则拦截
  4. 改为合法时长，成功提交预约
  5. 返回学术空间页，再输入贴近上一单结束后 `4` 分钟的新时间段，展示缓冲冲突
  6. 回到订单详情，执行取消
- 浏览器里可证明的点：
  - 学术空间采用连续时间而不是 slot
  - 规则限制真实进入前台主路径
  - `5` 分钟缓冲真实影响冲突判断
  - 订单取消后状态会更新
- 对应评分项：
  - `A`
  - `B`
  - `D`
- 是否进入主视频：
  - 必放

### 5.2 体育设施预约闭环链

- 涉及页面：
  - 体育设施 `/sports`
  - 我的订单 `/orders`
- 建议动作：
  1. 打开体育设施页
  2. 切到“组合预订”
  3. 选择一个组合目标和一个未来整点 slot
  4. 成功提交
  5. 返回时段表，展示整组场地对应 slot 已被占用
  6. 如彩排稳定，可切回单场模式说明该 slot 已不可再选
- 浏览器里可证明的点：
  - 体育设施按 `1` 小时离散 slot 展示和提交
  - 组合资源可以在前台直接理解
  - 提交后看到的是整组场地一起被占，而不是单个资源半成功
- 对应评分项：
  - `A`
- 是否进入主视频：
  - 必放

### 5.3 活动报名支付闭环链

- 涉及页面：
  - 活动页 `/activities`
  - 订单详情 `/orders/:orderId`
- 建议动作：
  1. 打开活动页
  2. 选择一个付费票
  3. 点击“立即报名”
  4. 先展示状态为 `queued`
  5. 等状态进入 `pending_confirmation`
  6. 打开订单详情页，展示：
     - 待支付状态
     - 支付截止时间
     - `PaymentRecord(PENDING)`
     - 金额
  7. 点击 `Mock Pay`
  8. 状态变为 `confirmed`
- 浏览器里可证明的点：
  - 热门活动不是直接同步成功，而是先排队
  - 活动订单有真实待支付阶段
  - 支付后状态真实变化
- 对应评分项：
  - `B`
  - `A`
- 是否进入主视频：
  - 必放

### 5.4 管理端规则中心收口链

- 涉及页面：
  - 首页 `/`
  - 管理端 `/admin`
  - 规则工作区
  - 活动管理或资源工作区
- 建议动作：
  1. 从首页切换到教师入口
  2. 打开规则工作区
  3. 展示规则类型与绑定关系
  4. 说明前面学术空间中的时长限制与规则拦截不是硬编码，而是从后台配置进入业务主链路
  5. 可再停留 `5–10` 秒展示活动工作区，让评委知道活动、票种与状态也有正式后台入口
- 浏览器里可证明的点：
  - 规则中心与前台行为存在对应关系
  - 后台工作区不是简单接口面板，而是业务域工作台
- 对应评分项：
  - `D`
  - `F`
- 是否进入主视频：
  - 建议放

## 6. 不进入主视频主体的能力

以下能力当前仓库有代码、文档或验证证据，但不适合放在浏览器主视频里展开：

### 6.1 适合答辩补充的能力

1. 幽灵支付对撞
2. 延迟取消 worker
3. 活动库存自愈
4. 爽约处罚落库
5. compose / CI / 自动化测试

### 6.2 原因

1. 这些能力在浏览器里要么不可见，要么需要长等待。
2. 强行塞进 `3–5` 分钟主视频会破坏节奏。
3. 评委在主视频里最需要先看到的是：
   - 业务是否扣题
   - 是否有异常拦截
   - 是否有状态流转

### 6.3 建议放置位置

- `README`
- `docs/architecture/*`
- `docs/verification/*`
- 答辩时口头补充
- 附件截图或补充材料

## 8. 每条主视频功能链的详细脚本

### 8.1 开场定位

- 起始画面：
  - 浏览器直接打开正式域名首页
- 先做什么：
  - 按一次 `Tab`
  - 让 `skip link` 或焦点可见态闪现
- 第二步做什么：
  - 点击学生入口
- 建议旁白：
  - `主视频里我只录这个域名打开的网站。这个系统不是把所有业务揉成一个预约页面，而是把学术空间、体育设施和热门活动用不同模型处理。`
- 关键词：
  - `同域名`
  - `统一入口`
  - `可访问性`
- 最想让评委记住：
  - 这是统一产品入口，不是多个零散 demo 页

### 8.2 学术空间预约闭环链

- 起始画面：
  - 停在 `/spaces`
  - 连续时间轴和右侧表单一起入镜
- 第一步：
  - 输入超过 `120` 分钟的时段
  - 展示“最长预约时长”规则拦截
- 第二步：
  - 改成合法时段
  - 成功提交
  - 跳到订单详情
- 第三步：
  - 返回 `/spaces`
  - 选同一资源单元
  - 输入贴近上一单结束后 `4` 分钟的新时段
  - 展示冲突拦截
- 第四步：
  - 回到订单详情
  - 执行取消
- 冲突/异常操作：
  - 超时长规则拦截
  - `5` 分钟缓冲冲突
- 状态动作：
  - 取消订单
- 建议旁白：
  - `学术空间这里展示的是连续时间，不是整点 slot。先看规则限制，再看正常预约成功，最后把新预约贴到上一个结束后 4 分钟，系统依然拦截，因为底层把前后 5 分钟缓冲也算进冲突区间。`
- 关键词：
  - `连续时间`
  - `5 分钟缓冲`
  - `规则限制`
  - `取消`
- 最想让评委记住：
  - 学术空间是比赛题目里最关键的扣题能力之一，而且这里能在浏览器里看见完整闭环
- 时间不够时怎么缩减：
  - 去掉取消，只保留“规则拦截 + 成功预约 + 贴脸冲突”

### 8.3 体育设施预约闭环链

- 起始画面：
  - 停在 `/sports`
  - 时段表和“组合预订”切换一起出现
- 第一步：
  - 切到“组合预订”
- 第二步：
  - 选择组合场地目标
  - 选择一个未来整点 slot
  - 成功提交
- 第三步：
  - 返回表格看整组场地一起被占用
- 冲突/异常操作：
  - 主视频不再额外构造第二次失败请求
  - 用占用结果反向证明“该 slot 已不可绕过”
- 状态动作：
  - 表格状态更新
- 建议旁白：
  - `体育设施不是学术空间换皮，而是严格按 1 小时 slot 调度。更关键的是它支持组合资源，所以提交后锁定的是一整组场地，而不是只成功一半。`
- 关键词：
  - `1 小时 slot`
  - `组合资源`
  - `整组占用`
- 最想让评委记住：
  - 体育设施和学术空间在底层是两套调度模型
- 时间不够时怎么缩减：
  - 只保留“组合预订成功后整组占用”

### 8.4 活动报名支付闭环链

- 起始画面：
  - 停在 `/activities`
  - 票种卡片和“我的报名状态”区域一起入镜
- 第一步：
  - 选择一个付费票
  - 点击“立即报名”
- 第二步：
  - 展示状态为 `queued`
- 第三步：
  - 等状态进入 `pending_confirmation`
  - 打开订单详情页
- 第四步：
  - 停 `2–3` 秒展示：
    - 订单状态
    - 支付截止时间
    - 支付记录
    - 金额
- 第五步：
  - 点击 `Mock Pay`
  - 状态变为 `confirmed`
- 冲突/异常操作：
  - 主视频不演幽灵支付
  - 只口头说明“极端边界放在自动化和答辩里补充”
- 状态动作：
  - `queued -> pending_confirmation -> confirmed`
- 建议旁白：
  - `活动链路和普通预约不同，它不会点击后立刻同步成功，而是先排队，再进入待支付状态，最后支付确认后才进入 confirmed。`
- 关键词：
  - `queued`
  - `pending_confirmation`
  - `Mock Pay`
  - `confirmed`
- 最想让评委记住：
  - 热点活动和订单状态机已经进入浏览器可见主链路
- 时间不够时怎么缩减：
  - 只保留“报名 -> pending_confirmation -> Mock Pay”

### 8.5 管理端规则中心收口链

- 起始画面：
  - 回到首页
  - 切换教师入口
- 第一步：
  - 打开 `/admin`
  - 进入规则工作区
- 第二步：
  - 展示规则类型和绑定关系
- 第三步：
  - 如时间还够，切到活动管理或资源工作区停留数秒
- 冲突/异常操作：
  - 不建议在主视频里临时改规则再回前台重试
- 状态动作：
  - 这一段主要是配置证明，不承担状态演示
- 建议旁白：
  - `前面浏览器里看到的限制和状态变化，并不是写死在前端里，而是有对应的后台工作区。这里能看到规则配置和业务管理入口。`
- 关键词：
  - `规则中心`
  - `工作区`
  - `不是硬编码`
- 最想让评委记住：
  - 前台行为背后有正式后台和规则配置，不是临时写死的 demo
- 时间不够时怎么缩减：
  - 只保留规则工作区 `10–15` 秒

## 9. 主视频功能链模板

- 功能名称：
  - 明确它要证明哪条比赛要求
- 正常操作：
  - 至少一次成功创建 / 成功支付 / 成功取消 / 成功流转
- 冲突 / 异常操作：
  - 至少一次被拦截
  - 优先选评委一眼能理解的失败
- 规则限制操作：
  - 能在浏览器里看到规则拦截结果最好
- 后续状态动作：
  - 至少展示一个后续动作：
    - 取消
    - 支付
    - 确认
    - 重新进入订单页观察状态
- 想证明的技术点：
  - 限制为 `2–3` 个词
- 对应评分项：
  - 明确写 `A/B/C/D/E/F`
- 适合的视频时长：
  - `30–75` 秒

可复用对象：

- 预约资源
- 抢票 / 报名活动
- 支付订单
- 取消订单
- 规则配置
- 后台管理

## 10. 比赛要求到浏览器片段的映射

| 比赛要求 | 对应浏览器片段 | 通过什么浏览器动作证明 | 评委可能的理解 |
| --- | --- | --- | --- |
| 学术空间连续时间 + `5` 分钟缓冲 | 学术空间闭环链 | 连续时间轴、超时长被拦、贴脸冲突被拦 | 学术空间模型真实独立 |
| 体育设施 `1` 小时 slot / 组合资源 | 体育设施闭环链 | 组合预订、整点 slot、整组占用 | 体育设施不是连续时间换皮 |
| 热门活动高并发与防超卖 | 活动闭环链 | `queued` 后再进入订单状态 | 系统具备排队削峰意识 |
| 订单状态机 | 活动闭环链 | `pending_confirmation -> confirmed` | 订单不是创建即结束 |
| 动态规则引擎 | 学术链 + 管理端规则中心 | 前台被规则拦截，后台存在规则工作区 | 规则不是硬编码 |
| 响应式 / a11y / Web 标准 | 开场 + 页面切换 | `skip link`、焦点可见、浏览器窄宽度视图 | 至少具备基础 Web 标准意识 |
| Docker Compose / CI / 自动化测试 | 不在主视频，转补充材料 | 主视频不证明，改在 README / 答辩补充 | 工程能力由材料补充，不挤占浏览器主线 |
| 创新性 / 展示表达 | 整体主线 | 用三个闭环证明三类模型，而不是页面巡礼 | 演示逻辑清楚，有记忆点 |

## 11. 风险预警

### 11.1 最适合主视频展示的内容

1. 学术空间预约闭环
2. 体育设施组合预约
3. 活动待支付到确认闭环
4. 管理端规则中心收口

### 11.2 不适合塞进主视频的内容

1. compose 与 CI
2. 全量自动化测试
3. 幽灵支付过程
4. 库存恢复过程
5. 爽约处罚过程

### 11.3 浏览器里最容易翻车的动作

1. 在体育页选到已被占用的 slot 还尝试演成功
2. 活动链路里选择错误票种，导致没有进入待支付状态
3. 学术空间第二次冲突演示时，时间没有真正落在缓冲区内
4. 在管理端临场修改规则，影响后续演示环境
5. 录屏时等待异步状态过久，导致节奏拖慢

### 11.4 建议的彩排原则

1. 先固定一套演示账号和资源
2. 先准备未来时间段，不现场即兴选时间
3. 活动链只演一次付费票
4. 管理端只看配置，不临场大改
5. 把浏览器主视频与答辩材料拆开，不混录

## 13. 最终精简录屏脚本

- 开场 `15` 秒：
  - `主视频里我只录这个域名打开的网站。这个系统不是把所有预约做成一个页面，而是把学术空间、体育设施和热门活动分别用不同模型处理。`
- 第 `1` 段：
  - 学术空间：
    - 超时长被拦
    - 合法预约成功
    - 贴脸缓冲冲突被拦
    - 取消订单
- 第 `2` 段：
  - 体育设施：
    - 组合预订
    - 选择未来整点 slot
    - 提交后看到整组占用
- 第 `3` 段：
  - 活动报名支付：
    - 报名进入 `queued`
    - 变成 `pending_confirmation`
    - 打开订单详情
    - `Mock Pay` 后进入 `confirmed`
- 第 `4` 段：
  - 管理端收口：
    - 打开规则工作区
    - 说明前面的限制和状态变化来自后台配置
- 结尾 `10–15` 秒：
  - `所以评委在浏览器里看到的，不只是几个页面，而是三种校园业务在同一网站里按不同模型运行，并且有真实的冲突拦截、规则限制和状态流转。`
