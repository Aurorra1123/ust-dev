# 比赛演示视频闭环脚本方案（2026-04-22）

## 1. 文档目的

- 将当前仓库真实可展示能力整理为一版适合 `3–5` 分钟比赛录屏的闭环式演示方案。
- 避免把前端页面巡礼误当作比赛演示主线。
- 让演示动作严格对齐比赛 PDF 的高分项，而不是平均点功能。

## 2. 当前判断

结论：当前仓库更适合做“技术亮点驱动的业务闭环型演示”，不适合做普通用户旅程型页面巡礼。

原因：

1. 当前系统最强的部分不是“页面数量”，而是三类不同业务模型背后的底层约束与状态一致性：
   - 学术空间：连续时间 + 前后 `5` 分钟隐形缓冲 + 排斥约束
   - 体育设施：`1` 小时离散 slot + 组合资源 + 整单原子性
   - 活动报名：`Redis + BullMQ + Worker + 统一订单状态机 + Mock Payment`
2. 如果只按首页、学术页、体育页、活动页、后台页逐页点过去，评委更容易把项目理解成“完成度较高的 Web 应用”，而不是“高度扣题的系统设计作品”。
3. 当前前端与后端已经具备足够多的“正常流程 + 冲突/规则拦截 + 状态变化”的真实链路，适合被组织成若干个短闭环。

## 3. 演示总策略

主线采用四段式：

1. 学术空间闭环：证明连续时间建模、`5` 分钟缓冲和规则拦截
2. 体育设施闭环：证明离散 slot、组合资源和整单一致性
3. 活动报名支付闭环：证明高并发骨架、待支付状态机和支付确认
4. 规则中心 + DevOps 证据收口：证明规则不是硬编码、项目具备一键启动和自动化验收意识

这套顺序优先争取：

- `A. 系统架构与领域建模`
- `B. 高并发与状态机处理`
- `D. 动态规则与代码质量`
- `E. DevOps 与自动化验收`

`C. 产品体验与 Web 标准` 与 `F. 创新性与展示表达` 通过轻量证据补充，不占主视频太多时长。

## 4. 适合视频展示的功能链清单

### 4.1 学术空间预约闭环链

- 涉及页面/模块：
  - 学生端 `/spaces`
  - 订单详情 `/orders/:orderId`
  - `apps/api/src/modules/reservation/reservation.service.ts`
  - `apps/api/prisma/migrations/20260417020123_academic_reservation_flow/migration.sql`
- 建议动作：
  1. 先输入超过 `120` 分钟的区间，触发最长预约时长规则拦截
  2. 改为合法区间，成功创建学术预约
  3. 再提交一笔贴脸相邻的新预约，请求时间落在缓冲区内，展示冲突拦截
  4. 打开订单详情，执行取消，展示状态变化
- 能证明的技术点：
  - 学术空间不是整点 slot，而是连续时间段建模
  - 冲突判断不是前端提示，而是业务层预检 + 数据库排斥约束双保险
  - 规则来自绑定关系，不是主流程里散落的 if-else
  - 成功、冲突、取消可以形成一个完整闭环
- 对应评分项：
  - `A`
  - `B`
  - `D`
- 是否值得放进最终视频：
  - 必放

### 4.2 体育设施预约闭环链

- 涉及页面/模块：
  - 学生端 `/sports`
  - `apps/api/src/modules/reservation/reservation.service.ts`
  - `apps/api/prisma/migrations/20260417023023_sports_slot_booking/migration.sql`
- 建议动作：
  1. 切到“组合预订”
  2. 选中 `Badminton Pair` 这类组合场地
  3. 选择一个未来整点 slot 成功提交
  4. 提交后回到时间表，展示该 slot 下两块场地一起变为不可再选
  5. 如彩排稳定，可切回单场模式说明同一 slot 不能绕开组合约束再次占用
- 能证明的技术点：
  - 体育设施是严格 `1` 小时 slot，而不是连续时间
  - 体育域支持组合资源，不是只做单场地预约
  - 任一成员冲突时整单失败，避免出现半成功半失败
  - 底层部分唯一索引拦截有效占用冲突
- 对应评分项：
  - `A`
- 是否值得放进最终视频：
  - 必放

### 4.3 活动抢票/支付闭环链

- 涉及页面/模块：
  - 学生端 `/activities`
  - 订单详情 `/orders/:orderId`
  - `apps/api/src/modules/activities/activity-registration.service.ts`
  - `apps/api/src/modules/payment/payment.service.ts`
  - `apps/api/src/modules/orders/orders.service.ts`
  - `apps/api/src/worker.module.ts`
- 建议动作：
  1. 选择一个已发布活动的付费票
  2. 点击报名，先展示 `queued`
  3. 等状态进入 `pending_confirmation`
  4. 打开订单详情，展示 `expireAt`、`PaymentRecord(PENDING)` 和金额
  5. 点击 `Mock Pay`，状态进入 `confirmed`
- 能证明的技术点：
  - 热点请求先排队，不直接同步打数据库
  - 活动订单并非创建即确认，付费链路已经进入真实待支付状态机
  - 支付记录与订单确认都收敛到统一订单中心
  - `worker` 是独立进程，不依赖 API 进程内异步
- 对应评分项：
  - `B`
  - `A`
- 是否值得放进最终视频：
  - 必放

### 4.4 规则中心联动链

- 能证明的技术点：
  - 规则执行通过 registry / handler 组织，不再继续堆进主业务流程
  - 规则具备即时启停与绑定关系
  - 前台拦截与后台配置形成闭环
- 对应评分项：
  - `D`
  - `A`
- 是否值得放进最终视频：
  - 建议放，但压缩在 `20–30` 秒

### 4.6 不建议放进主视频主线的功能链

以下能力已经有代码或验证证据，但不建议放进 `3–5` 分钟主视频里做过程型展示：

1. 幽灵支付对撞
   - 适合通过 `qa-003` 验证文档和代码入口做答辩补充
   - 不适合主视频现场等待“最后一秒支付 vs 超时取消”
2. 活动库存自愈 / Redis 冷恢复
   - 适合通过 `qa-004`、`comp-006` 说明
   - 不适合录屏里现场构造缓存异常
3. 爽约处罚链
   - 当前后端已有真实落库链路
   - 但从视频节奏上看，不如把时间留给三条主闭环
4. 全量自动化测试现场执行
   - 当前工作区复跑 `pnpm --filter api test` 结果为 `25` 个测试中 `20` 通过、`5` 失败
   - 因此主视频中不建议现场跑全量测试，只展示测试文件、CI 和验证文档

## 6. 每条最终入选功能链的录屏脚本

### 6.1 学术空间预约闭环链

- 起始画面：
  - 停在 `/spaces`
  - 让中间连续时间视图先入镜
- 用户先做什么：
  - 输入超过 `120` 分钟的时段
- 第二步做什么：
  - 展示被“最长预约时长”规则拦截
  - 将时段改为 `60` 分钟后成功提交
- 第三步做什么：
  - 回到 `/spaces`
  - 选同一资源单元，把新时段贴到上一个预约结束后 `4` 分钟，展示缓冲冲突
- 冲突/规则拦截出现在哪：
  - 第一步：规则限制
  - 第三步：`5` 分钟缓冲冲突
- 状态变化 / 后续动作在哪：
  - 打开订单详情后执行取消，状态改为 `cancelled`
- 建议旁白：
  - `学术空间不是按整点 slot，而是连续时间预约。这里先看到时长规则会直接拦截超额请求；真正成功创建后，再把下一单贴到前单结束后 4 分钟，系统仍然拦截，因为底层把前后 5 分钟缓冲一起算进冲突区间。`
- 关键词：
  - `连续时间`
  - `5 分钟缓冲`
  - `规则绑定`
  - `取消`
- 最想让评委记住什么：
  - 学术空间建模和冲突控制是真正扣题的，不是前端小提示
- 时间不够时如何缩减：
  - 保留“超时长被拦 + 合法预约成功 + 贴脸冲突”，删除取消动作

### 6.2 体育设施预约闭环链

- 起始画面：
  - 停在 `/sports`
  - 让 `单场地 / 组合预订` 切换和 slot 表一起出现
- 用户先做什么：
  - 切到“组合预订”
- 第二步做什么：
  - 选择组合场地目标
  - 选择一个未来整点 slot
  - 提交成功
- 第三步做什么：
  - 返回表格观察同一 slot 下整组场地一起被锁定
- 冲突/规则拦截出现在哪：
  - 不建议在主视频里再做第二次失败请求
  - 用表格状态反向证明“同 slot 已不可绕过”
- 状态变化 / 后续动作在哪：
  - 提交后表格状态即时变化
- 建议旁白：
  - `体育设施和学术空间完全不是一套调度模型。这里每个格子都是严格 1 小时 slot，而且支持组合资源；提交后锁定的是整组场地，因此不会出现只成功一半的静默冲突。`
- 关键词：
  - `1 小时 slot`
  - `组合资源`
  - `整单原子性`
- 最想让评委记住什么：
  - 学术与体育两类业务在底层被分开建模了
- 时间不够时如何缩减：
  - 只保留“组合预约成功 + 表格显示整组占用”

### 6.3 活动抢票/支付闭环链

- 起始画面：
  - 停在 `/activities`
  - 让票种、剩余额度和“立即报名”按钮同框
- 用户先做什么：
  - 点击一个付费票的“立即报名”
- 第二步做什么：
  - 让“我的报名状态”出现 `queued`
  - 等状态进入 `pending_confirmation`
- 第三步做什么：
  - 打开订单详情页
  - 停 `2–3` 秒给评委看清：
    - 订单状态
    - `expireAt`
    - `PaymentRecord(PENDING)`
    - 金额
- 冲突/规则拦截出现在哪：
  - 主视频中不展开对撞
  - 用口头说明“幽灵支付和延迟取消放在自动化证据里”
- 状态变化 / 后续动作在哪：
  - 点击 `Mock Pay`
  - 订单状态变 `confirmed`
  - 支付记录变 `paid`
- 建议旁白：
  - `热门活动不是同步打数据库，而是先进入排队状态，再由独立 worker 建单。付费票也不是创建即确认，而是先进入待支付状态；支付确认后，订单才通过统一状态机进入 confirmed。`
- 关键词：
  - `queued`
  - `worker`
  - `pending_confirmation`
  - `payment record`
  - `confirmed`
- 最想让评委记住什么：
  - 高并发入口和订单状态机是真实主链路，不是 PPT 设计
- 时间不够时如何缩减：
  - 保留“报名 -> pending_confirmation -> mock pay”

### 6.4 规则中心 + DevOps 证据链

  - 停在 `/admin`
  - 进入规则工作区
- 用户先做什么：
  - 展示规则类型与资源绑定范围
- 第二步做什么：
  - 说明学术空间前面的时长拦截就是从这里进入主链路
- 第三步做什么：
  - 切到 `README`、`judge-up.sh`、`docker-compose.yml`、`.github/workflows/ci.yml`

- 冲突/规则拦截出现在哪：
  - 不建议临场改规则并反复试，除非彩排完全稳定
- 状态变化 / 后续动作在哪：
  - 这一段主要展示配置和证据，不承担状态变化
- 建议旁白：
  - `前面的拦截不是写死在主流程里，而是从规则中心进入真实业务链。工程侧也不是靠手工演示交付，这里有一键 judge 启动、compose 拓扑、CI 和边界验证记录。`
- 关键词：
  - `rule registry`
  - `binding`
  - `judge-up`
  - `compose`
  - `CI`
- 最想让评委记住什么：
  - 项目不仅能演，还有交付纪律和验收证据
- 时间不够时如何缩减：
  - 只保留规则页 `10` 秒 + DevOps/verification `15` 秒

## 7. 功能链设计模板

- 功能名称：
  - 一句话说明它要证明哪条比赛要求
- 正常操作：
  - 必须有一次成功创建、成功支付、成功取消或成功状态流转
- 冲突/异常操作：
  - 优先选能体现底层约束的失败，不优先选普通表单校验
- 规则限制操作：
  - 尽量让后台规则配置和前台拦截形成对应
- 后续状态动作：
  - 至少选一个：
    - 取消
    - 支付
    - 确认
    - 超时
    - 签到 / 爽约
- 想证明的技术点：
  - 限制为 `2–3` 个最硬的词，例如：
    - `排斥约束`
    - `部分唯一索引`
    - `CAS 状态机`
    - `Redis + MQ + Worker`
- 对应评分项：
  - 明确写出 `A/B/C/D/E/F`
- 适合的视频时长：
  - `30–75` 秒

该模板可直接复用到：

- 预约资源
- 抢票 / 报名活动
- 支付订单
- 取消订单
- 规则配置
- 后台管理

### 9.5 当前工作区补充说明

## 10. 最终精简录屏脚本

- 开场 `15` 秒：
  - `这套系统不是把预约、抢票和订单塞进一个普通网站，而是按三种不同校园业务模型处理：学术空间用连续时间，体育设施用离散 slot，热门活动走异步排队和统一订单状态机。`
- 第 `1` 段：
  - 学术空间预约闭环：
    - 超时长被规则拦截
    - 合法预约成功
    - 贴脸缓冲冲突被拦
    - 订单取消
- 第 `2` 段：
  - 体育设施组合预约闭环：
    - 组合预订
    - 选择未来整点 slot
    - 提交后展示整组被占用
- 第 `3` 段：
  - 活动抢票/支付闭环：
    - 报名进入 `queued`
    - 进入 `pending_confirmation`
    - 订单详情展示支付记录
    - `Mock Pay` 后变 `confirmed`
- 第 `4` 段：
  - 规则中心 + DevOps 证据链：
    - 规则绑定
    - `judge-up`
    - `docker-compose`
    - `CI`
    - verification 文档
- 结尾 `15` 秒：
  - `所以这不是“能下单”的系统，而是把三类校园业务各自用正确的领域模型、约束和状态机处理，并且具备部署和验收证据的比赛级作品。`
