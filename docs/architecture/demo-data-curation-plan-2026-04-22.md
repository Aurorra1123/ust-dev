# 正式 Demo 数据整备方案（2026-04-22）

## 1. 文档目的

- 将当前系统中的演示数据从“开发样例”整理为“正式校园产品演示数据”。
- 去掉明显的脚手架与开发痕迹，例如：
  - `Room 101`
  - `Badminton Demo Courts`
  - `General Admission`
  - `demo`
- 在不修改数据库 schema 的前提下，让学生端与教师端页面都更接近最终产品观感。

## 2. 本轮原则

本轮只处理 demo 数据，不处理领域模型与数据库结构。

执行原则如下：

1. 保留稳定 `id`，尽量不改已有关联关系。
2. 重点替换展示字段，而不是重建整套 demo 数据模型。
3. 现有预约、抢票、规则、通知、工单主链路不能因为重命名而失效。
4. 数据数量保持克制，避免为了“看起来丰富”而堆过多样例。

## 3. 当前问题

当前 demo 数据虽然可用，但仍然有明显开发阶段痕迹：

1. 资源名称偏通用或偏英文样例。
2. 体育资源名称直接带有 `Demo` 痕迹。
3. 活动票种命名更像通用模板，不像正式校园产品。
4. 通知、工单、规则名称中仍有“演示用 / demo / workshop draft”一类痕迹。
5. 用户展示名称仍然偏测试账号风格。

这些问题不会影响功能，但会明显影响演示时的产品完成度。

## 4. 目标状态

演示数据应满足：

1. 看起来像真实校园产品会存在的数据。
2. 能清晰覆盖学术空间、体育场馆、活动、通知、工单和规则配置几条主线。
3. 与前端当前的信息架构保持一致：
   - 学术空间
   - 体育场馆
   - 活动管理
   - 通知发布
   - 工单维修
   - 规则配置

## 5. 数据整备范围

## 5.1 学术空间

目标：

- 资源命名更正式
- 编码更接近楼栋 / 区域命名
- 同时兼容当前学术空间前端分组逻辑

建议方向：

- `E1-INNOVATION-01`：创新协作室
- `E2-PROJECT-02`：项目讨论室
- `E3-SEMINAR-01`：学术研讨间

如果本轮仍只保留少量资源，也至少要把现有主学术空间改造成这种正式命名风格。

## 5.2 体育场馆

目标：

- 保留“单场地 + 组合场地”演示能力
- 去掉 `Demo Courts` 这类明显开发命名

建议方向：

- `SPORT-BADMINTON-A`：羽毛球馆 A 区
  - `A1 号场`
  - `A2 号场`
- 组合资源：
  - `双场联动场地`

如后续扩展，也优先加入正式资源，而不是“测试场地 1 / 2”。

## 5.3 活动与票种

目标：

- 保留“已发布活动 + 草稿活动”的结构
- 标题、票种、地点和时间都更像正式运营数据

建议方向：

- 已发布活动：
  - `校园开放日 2026`
  - 票种：
    - `普通入场名额`
    - `优先通行名额`
- 草稿活动：
  - `跨学科创新工作坊`
  - 票种：
    - `工作坊席位`

## 5.4 通知

目标：

- 保留“已发布 + 草稿”结构
- 标题与摘要看起来像真实运营通知

建议方向：

- `羽毛球馆分时维护通知`
- `校园开放日报名提醒`
- 草稿：
  - `创新工作坊预热通知`

## 5.5 工单

目标：

- 保留少量样例
- 标题、位置和备注像真实报修内容

建议方向：

- `创新协作室投影异常`
- `羽毛球馆空调风量异常`

## 5.6 规则

目标：

- 继续保留规则系统演示证据
- 名称从“技术样例名”调整为正式中文表达

建议方向：

- `学术空间最低信用分`
- `学术空间最长预约时长`
- `体育场馆预约角色限制`

## 5.7 用户显示名

目标：

- 登录账号可以保留
- 展示名应尽量减少“测试账号”气质

建议方向：

- `demo@campusbook.top` 的显示名可调整为正式学生姓名或示意姓名
- 管理员名称改成正式运营 / 教师角色名称

如果考虑到脚本和既有演示文档，本轮也可以只改页面暴露名称，不改登录账号本身。

## 6. 实施方式

本轮建议通过以下方式落地：

1. 以 `apps/api/src/scripts/seed-demo-data.ts` 为主修改入口。
2. 保留已有内部 `id`，减少对现有接口、测试和前端状态的影响。
3. 更新以下字段：
   - `code`
   - `name`
   - `description`
   - `location`
   - 活动标题与票种名
   - 通知标题 / 摘要 / 内容
   - 工单标题 / 位置 / 备注
   - 规则名称
   - 用户 `name`
4. 重灌本地或演示环境 demo 数据，做页面抽查。

## 7. 验收口径

完成后应满足：

1. 页面里不再出现明显的 `demo / draft workshop / general admission / room 101` 等开发痕迹。
2. 学术空间编码仍能正常驱动 `E1 / E2 / E3 ...` 分组逻辑。
3. 资源、活动、通知、工单、规则都更像正式产品展示数据。
4. 现有演示链路仍然可用：
   - 学术预约
   - 体育预约
   - 活动抢票
   - 规则命中
   - 通知与工单展示

## 8. 风险与边界

## 8.1 不建议直接改线上正式库

本轮默认作用对象应为：

- 本地 demo 库
- 演示专用环境

而不是线上正式运行库。

## 8.2 编码变更要兼容前端分组逻辑

如果学术空间 `code` 被改写，必须确认它仍符合当前前端按前缀分组的规则。

## 8.3 不做“大而全”的样例堆砌

本轮目标不是制造大量数据，而是提升每一条 demo 数据的质量与正式感。
