# 代码质量评估与重构基线（2026-04-21）

## 目的

本文件用于把当前仓库在代码组织、模块边界和实现风格上的主要问题固化为后续重构基线，避免问题只停留在聊天记录中。

本轮基线只记录“当前真实代码已经暴露出来的问题”和“后续重构必须遵守的边界”，不把尚未确认的未来能力写成设计目标。

## 评估标准

本轮评估统一按以下标准判断：

- 模块化与组件化
- 高内聚、低耦合
- 单一职责与清晰组织
- 简洁、高效、可读性高
- 反对过度设计
- 不补兜底代码、冗余代码、猜测性代码
- 对业务边界不清楚的地方优先提问，而不是用臆测补逻辑

## 当前结论

当前仓库整体已经具备按应用层和后端领域模块拆分的基础：

- 顶层存在 `apps/web`、`apps/api`、`packages/shared-types`
- 后端大体按 `auth / resource / reservation / orders / activities / notifications / service-requests / rules` 分域
- 管理端已引入 `workspace` 概念，方向上优于“一个后台大页面”

但从“真实代码组织质量”来看，当前主要问题不是“抽象太少”，而是“页面和工作区拆了名字，但很多职责还没有真正拆开”；其次是共享领域字典、输入归一化和错误契约没有形成单一事实来源，已经出现重复实现和语义漂移。

## 主要问题

### 1. 大页面与大工作区仍然承担过多职责

这是当前最主要的问题。

典型文件：

- `apps/web/src/ui/pages/spaces-page.tsx`
- `apps/web/src/ui/pages/sports-page.tsx`
- `apps/web/src/ui/pages/admin/workspaces/resources-workspace.tsx`
- `apps/web/src/ui/pages/admin/workspaces/rules-workspace.tsx`

问题表现：

- 同一文件同时负责：
  - 数据查询
  - 本地交互状态
  - 业务判断
  - 可视化数据推导
  - 表单提交
  - 页面渲染
- 页面内部 helper 与 JSX 深度交织，阅读时必须在文件上下来回跳转
- 很多逻辑虽然已经与“页面展示”无关，但仍停留在页面文件底部

直接证据：

- `spaces-page.tsx` 既负责 query window、冲突分析，也负责 timeline segment 生成、窗口相交判断、邮箱解析与 legend 渲染
- `sports-page.tsx` 既负责 group booking 目标选择和格子状态归纳，也负责状态文案、状态样式、成员名称摘要和邮箱解析
- `resources-workspace.tsx` 在一个文件里同时处理：
  - 资源列表选择
  - 资源启停与删除
  - 资源单元创建/删除
  - 批量作用目标
  - 预约开放策略
  - 预约关闭规则
  - 预约状态查询
  - 管理员取消预约
- `rules-workspace.tsx` 在单页内混合：
  - 规则列表
  - 创建/编辑
  - 启停/删除
  - 资源绑定
  - 规则摘要
  - 表达式转换
  - 局部错误映射

影响：

- 页面不再是“编排层”，而是事实上的“巨型控制器”
- 任何一个局部需求调整，都容易波及整页
- 很难做稳定复用，因为复用单元不是清晰模块，而是一大段耦合代码
- 代码可读性明显下降，维护者需要同时理解 UI、状态和业务规则

这类问题违反了：

- 模块化与组件化
- 高内聚低耦合
- 单一职责与清晰组织
- 可读性高

### 2. 共享领域字典与输入归一化没有单一归口，已经出现重复与漂移

当前前端里已经出现同类逻辑在多个文件各写一份的情况。

典型重复：

- `serviceRequestStatusLabel` / `serviceRequestStatusTone`
  - 学生端在 `apps/web/src/ui/pages/service-requests-page.tsx`
  - 后台在 `apps/web/src/ui/pages/admin/admin-helpers.ts`
- `parseCompanionEmails`
  - 学术预约页在 `apps/web/src/ui/pages/spaces-page.tsx`
  - 体育预约页在 `apps/web/src/ui/pages/sports-page.tsx`

更严重的是已经出现语义漂移：

- 学生侧把 `no_show` 渲染成“已结束 / Finished”
- 后台把 `no_show` 渲染成“已爽约 / No-show”

这说明：

- 这些逻辑并不是“页面私有细节”
- 它们已经是领域展示规则
- 但当前没有单一 owner 模块来维护

此外，首页服务卡片当前仍通过判断中文标题字符串来决定英文文案分支：

- `apps/web/src/ui/pages/home-page.tsx`

这类写法的问题是：

- 文案与业务 key 混在一起
- 一旦中文标题调整，英文映射就会跟着失效
- 这不是稳定的数据驱动，而是对当前文案值的耦合

影响：

- 相同状态在不同页面上的语义可能不一致
- 后续国际化、重命名或批量调整时风险高
- 维护者无法快速判断“这类规则应该去哪里改”

这类问题违反了：

- 单一组织
- 高内聚低耦合
- 简洁与可读性

### 3. API 错误契约过于依赖裸字符串，前后端边界耦合过深

当前后端很多异常仍以字符串作为唯一契约：

- 简单 code：`resource-not-found`
- 拼接 code + 数据：`companion-users-not-found:${emails}`
- 拼接 code + 业务对象 + 时间：`resource-booking-closed:${resource.name}:${startsAt}:${endsAt}`

典型位置：

- `apps/api/src/modules/reservation/reservation.service.ts`
- `apps/api/src/modules/activities/activity-registration.service.ts`

前端基础层 `ApiError` 目前只保留 `message`：

- `apps/web/src/lib/http/errors.ts`

页面层又大量直接展示这个 message：

- 登录页
- 预约页
- 活动页
- 订单页
- 多个管理员 workspace

问题本质：

- 后端把“机器可判断的错误码”和“可展示给用户看的文案”混在一起
- 前端又把“内部异常 message”直接当用户文案使用
- 一旦 message 结构变化，页面就会一起受影响

这会带来两个后果：

1. 前端难以做统一的错误文案翻译和归类
2. 后端返回里混入资源名、邮箱、时间等动态片段后，message 更像临时协议而不是清晰边界

这类问题不是“防御不足”，恰恰相反，它是一种为了快速覆盖场景而形成的脆弱耦合。

这类问题违反了：

- 高内聚低耦合
- 单一组织
- 简洁高效可读

### 4. HTTP 基础层存在猜测性 fallback

`apps/web/src/lib/http/client.ts` 当前会按以下顺序决定 API base URL：

1. 运行时配置
2. 环境变量
3. 主机名推断

其中主机名推断会对未知 hostname 默认猜到 `api.campusbook.top`。

问题不在“能不能工作”，而在于这类逻辑本质上是猜测性代码：

- 它依赖作者对未来部署环境的猜测
- 真实运行环境越多，这种猜测越容易失效
- 它让错误配置不容易第一时间暴露

如果仓库只支持明确的几种部署方式，显式配置要比 host heuristic 更符合当前工程目标。

这类问题违反了：

- 不补猜测性代码
- 不为追求“保险”而堆冗余分支

### 5. 局部页面内部仍然保留文案驱动逻辑和页面级小工具堆积

这类问题没有前几项严重，但会持续拉低代码可读性。

典型表现：

- 页面底部堆积大量只在单文件可见的小函数
- 状态 class、label、summary、parser 都直接挂在页面底部
- 页面里通过当前标题/当前文案去推导另一种文案，而不是使用稳定字段

这些问题单看不大，但聚集起来会让：

- 页面越来越像脚本文件
- 组件化边界越来越模糊
- 后续重构成本越来越高

## 重构原则

后续重构必须遵守以下原则：

### 1. 先按职责拆，再谈抽象

优先把一个大页面拆成：

- 页面容器
- 领域视图组件
- 领域派生 helper
- 输入归一化 helper

不要一上来抽“万能 hook / 通用 builder / 配置驱动页面”。

### 2. 共享逻辑必须有单一 owner

以下内容一旦跨页面复用，就不能继续散落在页面内部：

- 状态标签与状态 tone
- 领域术语映射
- 输入解析与归一化
- 订单/工单/规则等展示语义

应明确放到：

- 领域 helper
- 共享 UI 文案模块
- 对应页面域下的本地 `helpers` / `view-model` 文件

### 3. 页面容器只保留编排职责

页面文件应优先负责：

- 组装 query / mutation
- 连接 store / route
- 把数据传给子组件

不应继续承担：

- 大段视觉推导
- 重复状态字典
- 输入解析
- 一整套业务判断细节

### 4. 先消除重复，再防止漂移

像 `parseCompanionEmails`、工单状态字典、活动状态字典、订单状态映射这类逻辑，后续应先收口，再统一语义。

如果还没收口，就不应继续在新页面里复制第三份、第四份。

### 5. 错误边界要从“裸字符串”收敛到“稳定 code + 可选 metadata”

目标不是引入复杂错误框架，而是把当前脆弱协议收口成更清晰的边界：

- code 负责让前端判断类型
- metadata 负责携带动态数据
- 页面负责把 code 映射为用户文案

不再继续把动态业务信息直接拼进 message 当唯一契约。

### 6. 不为了“可能以后会用到”而预埋大而全结构

后续拆分时禁止出现以下倾向：

- 没有明确复用就先抽通用工厂
- 没有稳定模式就先做配置化渲染器
- 没有真实第二个场景就先抽抽象接口层

重构目标是让代码更直接、更清晰，不是把它包得更深。

## 第一批重构目标

建议后续按以下顺序推进。

### 第一阶段：先收口共享小逻辑

优先收口：

- 同行人邮箱解析
- 工单状态 label / tone
- 活动状态 / 订单状态的用户侧展示字典
- 首页服务卡片的稳定 key 与双语文案映射

目标：

- 先消除重复和语义漂移
- 让后续拆页面时不再继续复制逻辑

### 第二阶段：拆学生端预约页面

优先拆：

- `spaces-page.tsx`
- `sports-page.tsx`

建议拆分边界：

- container
- 资源列表/目标列表组件
- 时间视图组件
- 预约表单组件
- 页面私有 helper 文件

目标：

- 页面只保留编排
- 视图推导和输入解析搬离 JSX 主体

### 第三阶段：拆管理员资源工作区

优先拆：

- 资源列表面板
- 当前资源结构面板
- 预约开放概况面板
- 预约状态面板
- 新建资源/单元/关闭规则/开放策略表单

目标：

- 把“一个巨大 workspace”拆成清晰子域
- 每块只负责一个可理解的维护任务

### 第四阶段：收口规则工作区

优先拆：

- 规则列表
- 规则编辑器
- 资源绑定面板
- 规则摘要面板
- 表达式转换 helper

目标：

- 避免规则编辑、绑定、摘要和错误映射继续混在同一文件

### 第五阶段：重构错误契约

优先范围：

- reservation
- activities
- resource
- rules

目标：

- 不再新增字符串拼接型 message 协议
- 前端不再直接把内部异常 message 当最终用户文案

## 明确不做的事情

本轮后续重构明确不做以下事情：

- 不把所有页面统一改成配置驱动渲染
- 不为了“通用性”先引入新的前端状态框架
- 不把所有 helper 一次性抽到全局 shared，导致新的全局耦合
- 不顺手改业务规则语义，除非重构过程中发现当前实现已经与产品要求冲突

## 验收标准

后续重构完成后，至少应满足：

1. 学生端预约页和后台资源工作区不再由单个超大文件承担主要职责
2. 工单状态、预约输入解析等共享逻辑存在单一 owner
3. 同一业务状态在学生端与后台的语义不再漂移
4. 新增页面不再通过标题字符串推导英文文案
5. API 错误边界开始收口，不再扩散新的字符串拼接协议

## 备注

本文件是“重构基线”，不是最终方案说明。后续如果拆分过程中发现某些问题比当前判断更浅或更深，应在不违背本文核心原则的前提下修正文档。
