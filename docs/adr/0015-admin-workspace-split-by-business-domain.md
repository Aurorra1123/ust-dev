# 0015 管理员工作台按业务域拆分一级模块

## 背景

当前管理员端虽然已经从“大一统页面”拆成多个 workspace，但一级导航仍然保留了明显的技术实现视角：

- `resources`
- `activities`
- `rules`
- `notifications`
- `serviceRequests`

这套结构对开发者是合理的，但对真实管理员并不自然。用户已经明确提出后台希望围绕以下业务对象来组织：

- 运营总揽
- 体育场馆
- 学术空间
- 活动管理
- 工单维修
- 通知发布

其中最关键的问题有两个：

1. “资源工作区”把体育设施和学术空间混在一起，违背管理员的业务认知。
2. “规则工作区”作为一级入口暴露过强，但它在当前演示版里属于低频、难解释的能力，不应继续占据后台主路径。

## 决策

本项目对管理员前端一级信息架构的当前阶段处理方式明确如下：

1. 管理员端一级模块调整为：
   - 运营总揽
   - 体育场馆
   - 学术空间
   - 活动管理
   - 工单维修
   - 通知发布
2. 现有“资源工作区”拆成两个独立业务模块：
   - 体育场馆
   - 学术空间
3. 学术空间默认按资源 `code` 前缀组织为 `E1 / E2 / E3 / E4 ...` 区域；无法识别前缀时进入兜底分组。
4. 活动管理、工单维修、通知发布在本轮保持现有实现，只调整命名和导航位置。
5. 规则工作区从管理员一级导航中下线。
6. 规则引擎后端能力与现有接口继续保留，本轮不删除。
7. 本轮优先做前端信息架构重组，不同步改后端接口与数据库模型。

## 明确不采用的方案

本轮明确不采用以下做法：

- 继续保留“资源工作区 + 规则工作区”的旧一级结构
- 把体育和学术资源继续混在一个页面里，只增加筛选器
- 同时重构前端导航、后端接口和数据库模型
- 因为隐藏规则入口就直接删除规则系统

这些方案分别会继续保留认知噪音、只做表面修补、扩大变更风险，或误删现有能力。

## 影响

正向影响：

- 管理员后台的命名和结构更接近真实业务语言
- 体育场馆与学术空间的操作上下文更清晰
- 规则工作区不再继续干扰管理员主路径
- 本轮可在不改后端协议的前提下完成大部分体验重组

需要注意的影响：

- 规则系统仍然存在，但不再有一级主入口，后续如果要恢复运营入口，需要重新设计
- 学术空间分组依赖资源编码规范，短期内需要接受“未分区”兜底
- 当前资源工作区的通用逻辑需要进一步抽共享层，否则容易在两套页面里产生复制

## 后续动作

1. 新增正式方案文档，记录本次管理员前端重组的实施边界与分阶段计划。
2. 在 `docs/plans/feature-list.json` 中新增 `ADM-*` 任务，作为后续开发排期入口。
3. 实施时优先拆管理员导航与资源工作区壳层，不把本轮拖成后端重构。
