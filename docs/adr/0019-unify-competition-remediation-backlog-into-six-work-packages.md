# ADR 0019: 将比赛整改方案收束为唯一主 backlog，并拆成六个不重叠工作包

## 背景

到 `2026-04-22` 为止，仓库里已经存在多份与比赛整改相关的文档：

- 核心偏题审查
- 最终验收与模拟打分
- 测试自动化计划
- 面向比赛 PDF 要求的整改计划
- 比赛缺口收口计划

这些文档分别回答了“哪里失分”“怎么验证”“PDF 怎么解释”和“下一步大概做什么”，但其中涉及的开发工作大量重叠：

- 支付闭环、`PENDING_CONFIRMATION`、`PaymentRecord`、幽灵支付
- 规则引擎扩展与处罚闭环
- 前端非功能证据
- 自动化测试与 judge 留证

同时，还有一块活动库存一致性、Redis 补偿与 `totalQuota` 口径问题，虽然在验收文档和 PDF 计划里明确存在，但没有被单独收口到正式 backlog，存在后续开发被漏掉的风险。

## 决策

确认以下文档收束策略：

1. `docs/plans/competition-gap-closure-plan-2026-04-22.md` 成为比赛整改的唯一执行 backlog。
2. `docs/review/` 下的相关文档继续保留，但只作为问题输入、测试矩阵输入或 PDF 解释输入，不再并行承担主开发排期职责。
3. 为避免重写已有历史记录，保留现有 `COMP-001` ~ `COMP-005` 的既有语义，不做整体重编号。
4. 新增 `COMP-006`，专门承接“活动库存一致性与 totalQuota 收口”这一块独立开发工作。
5. 以后讨论任务顺序时，执行顺序和任务编号分开表述；不得再默认“编号顺序等于开发顺序”。

## 影响

正面影响：

- 后续排期、开发和答辩都有唯一入口，不再需要在多份文档之间来回拼接。
- 支付、库存、规则、前端非功能、测试五类工作被真正拆开，减少重复开发和责任混淆。
- 活动库存一致性不再是“大家都提过，但没人单独接手”的遗漏项。

需要注意的影响：

- 因为保留了历史编号，最终执行顺序会出现 `COMP-006` 插在 `COMP-002` 和 `COMP-003` 之间的情况，文档必须写清楚。
- 旧进度记录里提到的 `COMP-003` ~ `COMP-005` 仍然保留其当时语义，新的执行顺序要以本次收束后的主计划为准。
- 未来若再新增比赛整改工作包，也应优先增量扩展，不随意重写历史编号。

## 后续动作

1. 更新主计划文档，写明唯一入口、六个工作包和最终执行顺序。
2. 更新 `docs/plans/feature-list.json`，补入 `COMP-006`。
3. 更新 `docs/progress/agent-progress.md`，记录本次方案收束动作。
