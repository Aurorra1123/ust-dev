# ADR 0027: demo seed 在整理正式演示数据前先重置演示环境

## 背景

当前演示环境已经长期混入联调过程中产生的历史资源、活动、工单、订单、预约和限制记录。

如果 `seed:demo` 只做增量 upsert，会持续留下两个问题：

1. 正式演示数据和历史测试数据并存，教师端与管理员端页面会越来越脏。
2. Redis 里的库存、pending key 和延迟任务可能继续引用已经不再属于正式演示集的数据。

这类问题不适合靠手工删几条资源解决，因为脏数据不只存在于主数据，还会蔓延到订单、预约、活动库存和限制状态。

## 决策

确认 `apps/api/src/scripts/seed-demo-data.ts` 的职责从“增量补 demo 数据”升级为“重置演示环境后再灌正式演示基线”。

具体要求：

1. seed 开始前清空当前 schema 中除 `_prisma_migrations` 以外的业务数据。
2. seed 开始前清空当前 Redis DB，移除活动库存、pending key 和 BullMQ 历史任务。
3. seed 再写入唯一正式演示基线，确保用户、资源、活动、通知、工单和规则都回到受控状态。
4. 后续演示环境若需要“恢复纯净基线”，统一通过 `seed:demo` 完成，而不是手工删库表记录。

## 影响

正面影响：

- 演示环境可以稳定回到单一、可预期的正式数据集。
- Redis 与数据库状态同步回到干净基线，避免历史任务继续污染演示。
- demo 数据整理工作变成可重复执行的运维动作，而不是一次性手工修库。

需要注意的影响：

- 执行 `seed:demo` 会清空当前演示库中的历史订单、预约、报名、工单处理记录和限制状态。
- 运行 seed 时应视为一次“演示环境重置”，不适合在需要保留历史业务痕迹的环境中直接执行。

## 后续动作

1. 调整部署流程：演示环境需要重置时，先停相关容器，再执行 `seed:demo`，最后重启 API/worker。
2. 保持正式 demo 用户、资源、活动和规则 id 稳定，便于前端演示脚本与验证文档复用。
3. 若未来新增正式演示场景，应继续通过 seed 基线维护，而不是在线上手工补数据。
