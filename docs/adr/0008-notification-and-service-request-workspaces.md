# 0008 通知与报修工作区闭环

## 背景

`PUX-006`、`APP-017`、`APP-018` 与 `PUX-010` 收口前，仓库存在以下问题：

- 学生首页通知区仍是空占位，没有真实数据链路
- 管理员工作台没有通知编辑/发布入口
- 学生端不存在报修工单入口，管理员端也没有统一收件视图
- 学生端多语言覆盖不完整，订单页与取消记录页职责仍有重叠

如果继续把通知、工单或学生端补丁做成单页硬编码，会把已有的“按工作区拆后台”方向重新拉回大页面拼接。

## 决策

本轮按以下方式实现通知与报修闭环：

1. 后端新增独立 `notifications` 模块：
   - 公共端只读取 `published` 通知
   - 管理端通过 `admin/notifications` 统一创建、编辑、发布
2. 后端新增独立 `service-requests` 模块：
   - 学生端只提交和查看自己的工单
   - 管理端统一查看所有工单并更新状态、备注
3. Prisma 新增：
   - `Notification`
   - `ServiceRequest`
   - 对应状态枚举
4. 管理端继续沿用 workspace 结构，不新增新的后台路由层级：
   - 通知作为 `notifications workspace`
   - 工单作为 `serviceRequests workspace`
5. 学生端保持主导航闭环：
   - 首页直接展示通知
   - 报修工单作为学生主导航入口
   - “我的订单”与“取消记录”分离，避免重复历史
6. demo seed 不再假设 demo 用户主键固定：
   - 先 `upsert` 用户
   - 再引用真实返回的用户 ID 写通知与工单

## 明确不采用的方案

本轮明确不采用以下方案：

- 把通知挂到活动模块内部作为活动附属字段
- 把工单塞回规则或资源工作区的临时表单
- 继续用首页硬编码文案模拟通知样例
- 通过新增单独 `/admin/notifications` 前端页面绕开既有 workspace 架构

原因是这些方案都会削弱现有边界，且会让学生端与管理员端看到不同步的数据源。

## 影响

正向影响：

- 学生首页通知与管理员通知发布共享单一事实来源
- 学生报修与管理员处理形成真实闭环，而不是演示文案
- 管理员工作台保持单一工作区切换入口，没有回退到冗余导航说明块
- demo seed 在已有数据库上更稳健，不再依赖固定 demo 用户主键

需要注意的影响：

- Prisma schema 与 migration 继续扩张，后续若再加站内消息或客服系统，需要明确与 `Notification` / `ServiceRequest` 的边界
- 当前通知仍是通用通知模型，没有绑定活动 ID；若后续需要“活动详情自动生成通知”，应另立任务扩展
- 当前工单状态仍是轻量流程，未实现指派、附件、评论流

## 后续动作

1. 若要继续产品化通知，可增加排序、置顶、跳转链接与发布时间窗口
2. 若要继续产品化工单，可增加处理人、附件、分类与 SLA 字段
3. 若要把本轮实现纳入更强验证，后续应补一组学生提交通知/工单到管理员查看的浏览器级回归证据
