# ADR 0018: 付费活动票作为支付闭环与幽灵支付收口的首条主链路

## 背景

赛题核心偏题审查已经明确：

- 资源建模、学术缓冲、体育 slot、活动高并发与一键拉起已经基本命中核心考点。
- 当前最大的失分项不是“有没有订单状态枚举”，而是“支付是否真的进入主链路，且能否处理幽灵支付”。
- 现有代码虽然有 `PENDING_CONFIRMATION`、`PaymentRecord`、延迟取消 worker 与 CAS 骨架，但主要业务链路仍大量直接写成 `CONFIRMED`。

如果此时直接把所有学术空间、体育预约和活动报名都统一改造为支付订单，范围会过大，也会显著增加回归风险。

## 决策

确认以下收口策略：

1. 支付闭环与幽灵支付的首条真实主链路，优先落在“付费活动票”而不是全部预约类型。
2. 统一使用 `红鸟音乐节` 的 `5` 元普通票作为计划、演示、测试与答辩的固定业务样例。
3. 本阶段采用 mock 支付发起与 mock 支付回调，不优先接第三方真实支付渠道。
4. 免费活动票、学术空间预约和体育预约暂不强行改造成待支付订单，避免为了补赛题而重写已经稳定的主链路。
5. 在付费活动票链路中，必须同时补齐：
   - `PENDING_CONFIRMATION`
   - `expireAt`
   - `PaymentRecord`
   - 支付回调幂等
   - 超时取消与支付成功的 CAS 对撞保护

## 影响

正面影响：

- 能以最小改动补齐当前最关键的失分点。
- 演示、测试和 judge 回归可以围绕一个固定样例收口，减少解释成本。
- 不会把学术空间和体育预约现有稳定逻辑一并拉入高风险重构。

需要注意的影响：

- 订单系统会在一段时间内同时存在“直接确认链路”和“待支付链路”，文档与代码边界必须写清楚。
- mock 支付虽然足够支撑比赛答辩，但后续若要接第三方支付，还需要补渠道适配与对账边界。
- 活动付费链路一旦先打通，后续扩展到其他付费场景时，应优先复用同一套状态机与补偿机制，而不是再起第二套逻辑。

## 后续动作

1. 实施 `COMP-001`，让 `红鸟音乐节 5 元普通票` 成为首个真实 `PENDING_CONFIRMATION` 订单样例。
2. 实施 `COMP-002`，补齐幽灵支付对撞、幂等与补偿验证。
3. 在 `COMP-005` 中把该样例纳入 judge smoke 和自动化回归。
