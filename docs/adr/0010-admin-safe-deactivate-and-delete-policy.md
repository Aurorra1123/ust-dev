# 0010 管理端采用“启停优先 + 无引用安全删除”策略

## 背景

用户测试明确指出，管理员当前无法撤销错误配置：

- 资源无法删除
- 资源单元无法删除
- 规则只能看快照，缺少启停、解绑和删除入口

如果直接对资源、资源单元和规则一律开放物理删除，会带来两个问题：

1. 已存在订单、预约历史和资源绑定时，删除会破坏可追溯性
2. 为了给 `ResourceUnit` 增加“归档状态”，需要额外改 Prisma 模型、映射和前后端数据结构，本轮成本明显高于当前明确需求

当前更迫切的需求不是“所有对象都必须有完整生命周期状态机”，而是“管理员能够安全撤销错误配置，同时不破坏历史数据”。

## 决策

本轮起，管理端对资源、资源单元和规则采用以下统一策略：

1. `Resource`：
   - 优先使用现有 `status` 做启用 / 停用
   - 只有在没有资源单元、规则绑定、通道规则和预约 / 订单历史时，才允许物理删除
2. `Rule`：
   - 优先使用现有 `status` 做启用 / 停用
   - 只有在未绑定任何资源、没有相关画像引用时，才允许物理删除
3. `ResourceUnit`：
   - 本轮不新增状态字段
   - 只提供“无引用时安全删除”
   - 一旦存在预约记录、订单记录或组合场地绑定，则阻止删除并给出明确原因
4. 所有危险操作必须带确认提示，并在界面上给出进行中、成功、失败反馈

## 明确不采用的方案

本轮明确不采用以下方案：

- 为了实现“资源单元归档”而立即修改 Prisma 数据模型
- 对仍被预约历史、订单历史或资源绑定引用的对象强行物理删除
- 继续把配置撤销能力留给数据库手工操作，而不是在管理端暴露

这些方案的问题分别是：

- 容易为了尚未被证明稳定的抽象过早扩大改动面
- 会让运营纠错能力与数据安全直接冲突
- 会让后台工作区继续停留在“可看不可管”的半成品状态

## 影响

正向影响：

- 管理员现在可以直接在工作区停用资源或规则，或安全删除未被引用的错误配置
- 历史预约、订单和绑定关系不会因误删而丢失
- 实现保持在当前最小必要范围内，没有为了单一需求引入额外 schema 迁移

需要注意的影响：

- `ResourceUnit` 目前仍没有独立的“停用 / 归档”状态，只有安全删除
- 如果后续确认资源单元确实存在长期“保留历史但不再开放”的运营场景，再补状态字段会更合理
- 删除能力当前是保守策略，宁可阻止也不冒险级联删除

## 后续动作

1. 若后续 `REG-001` 复测显示资源单元仍需“保留但不开放”，再评估是否为 `ResourceUnit` 新增状态字段
2. 后续继续审计管理端其他写操作的反馈一致性，逐步完成 `UTG-007`
3. 若未来扩展更多后台实体，沿用“启停优先、无引用安全删除”的默认策略，除非业务明确要求完整归档模型
