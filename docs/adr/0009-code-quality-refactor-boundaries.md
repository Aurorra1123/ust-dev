# 0009 代码质量重构边界与原则

## 背景

在完成一轮针对当前仓库真实代码的静态 review 后，已经明确暴露出以下持续性问题：

- 学生端预约页与后台工作区存在多个超大页面文件，职责混杂
- 共享领域字典、输入归一化和展示语义没有单一 owner，已经出现重复实现与状态语义漂移
- 前后端错误边界大量依赖裸字符串，部分 message 还混入动态业务数据
- HTTP 基础层仍保留基于 host 的猜测性 fallback

如果后续继续按“功能来了就往当前页面继续加”的方式推进，仓库会继续恶化为：

- 页面越来越大
- 重复实现越来越多
- 重构成本越来越高
- API 与前端页面耦合越来越深

因此需要先把后续重构的边界和原则固定下来。

## 决策

本轮确认以下长期生效的重构决策：

1. 页面与工作区优先按职责拆分，而不是先引入新的“通用页面框架”
   - 页面容器只保留编排职责
   - 领域派生逻辑、输入解析和复杂视图推导移到局部 helper / 组件
2. 共享领域字典必须有单一 owner
   - 工单状态
   - 订单状态展示语义
   - 活动状态展示语义
   - 同行人邮箱解析
   - 其他跨页面复用的展示规则
3. 后续重构明确反对“过早抽象”
   - 没有稳定重复，不新增通用工厂
   - 没有第二个真实场景，不新增抽象接口层
   - 不把简单逻辑包装成名义化框架
4. API 错误边界开始从“裸字符串 message”收口到“稳定 code + 可选 metadata”
   - 后端不再继续扩散字符串拼接协议
   - 前端不再把内部异常 message 直接当最终用户文案
5. 基础设施层不再继续增加猜测性 fallback
   - 配置优先显式
   - 对环境的支持应来自明确配置，而不是 host 猜测

## 明确不采用的方案

本轮明确不采用以下方向：

- 把所有页面改成统一配置驱动渲染
- 引入新的前端状态框架来掩盖当前文件过大的问题
- 为了“未来可能复用”而先抽全局万能 helper
- 继续允许同一业务状态在不同页面各自维护一套 label/tone 逻辑
- 继续用拼接后的异常字符串作为稳定前后端协议

原因是这些方案都会增加额外复杂度，不能解决当前最核心的“职责混杂”和“边界失真”问题。

## 影响

正向影响：

- 后续重构会围绕真实问题推进，而不是围绕形式上的“更抽象”
- 页面与工作区可读性会提升
- 共享领域规则会有清晰归口，避免继续漂移
- API 与前端的边界会更清晰，后续国际化和错误映射更可控

需要注意的影响：

- 初期会新增一些局部 helper / 子组件 / view-model 文件
- 文件数量会增加，但这是为了换取更清晰的职责边界
- 局部文件名和目录层级需要统一风格，避免“拆了但更乱”
