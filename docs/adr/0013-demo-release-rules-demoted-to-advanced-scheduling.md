# 0013 演示版前端将放号规则降级为高级调度设置

## 背景

`UTG-010` 的复审里，用户对“放号规则”的直接反馈是体验怪、意义不清，甚至倾向于隐藏。进一步检查当前系统后，可以确认两件事：

1. 后端的放号规则并不是无效能力。资源一旦存在有效放号规则，就会在放号前进入 `scheduled` 状态，并阻止用户立即预约。
2. 当前 demo 主路径里，管理员更常用也更容易解释的是“预约关闭规则”；而放号规则既没有出现在种子数据主流程里，也缺少足够强的展示语义支撑。

如果继续把放号规则和关闭规则并列放在资源工作区主路径，管理员会被迫面对一个“技术上存在、演示上却不好解释”的能力；但如果直接删除前端或后端能力，又会丢失已有的延迟开放场景支持。

## 决策

本项目对放号规则的当前阶段处理方式明确如下：

1. 后端继续保留放号规则模型、接口和调度语义，不做删除。
2. 前端资源工作区默认主路径只突出“预约关闭规则”，不再把放号规则与其并列暴露。
3. 放号规则在前端改名为“预约开放策略”，并收进“高级调度设置”。
4. 若资源已经存在开放策略，则该设置区继续默认展开并显示现有策略和下次开放时间。
5. 若资源没有开放策略，则默认收起，只在管理员主动展开高级设置时才显示配置表单。
6. 面向管理员和学生端的状态文案统一从“放号 / 待放号”收口为“开放 / 待开放”，降低技术口吻。

## 明确不采用的方案

本轮明确不采用以下做法：

- 直接删除后端放号规则能力
- 继续把放号规则长期放在资源工作区主路径，与关闭规则同级暴露
- 在前端彻底隐藏已有放号策略，导致资源明明受策略影响却看不到原因

这些方案分别会带来能力损失、演示噪音或状态不可见的问题，不适合作为当前 demo 阶段的平衡点。

## 影响

正向影响：

- 管理员默认操作路径更聚焦，资源工作区首屏噪音降低
- 系统仍保留“延迟开放预约”的能力，不影响已有模型和调度逻辑
- 对已经配置了开放策略的资源，前端仍会保留可见性，不会形成隐性状态

需要注意的影响：

- “预约开放策略”现在是一个偏高级能力，后续新增演示脚本或培训说明时，应避免把它当作默认必讲功能
- 若未来产品明确把延迟开放作为高频运营能力，需要再评估是否恢复更强的可见性和场景说明

## 后续动作

1. 后续若处理 `UTG-005` 或其他管理员体验项，应继续优先压缩默认演示路径中的低频能力噪音
2. 若未来 demo seed 引入真实“延迟开放”案例，应补对应说明文案或示例数据，而不是只恢复表单暴露
