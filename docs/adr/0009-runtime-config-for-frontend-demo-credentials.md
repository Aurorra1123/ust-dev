# 0009 前端 demo 凭据必须走运行时配置

## 背景

本轮排查真实站点时，发现“学生入口 / 教师入口”快捷填充虽然在前端页面上可见，但填入的密码与后端实际接受的 demo 密码不一致。

问题根因有两层：

1. `apps/web/src/ui/demo-accounts.ts` 曾直接写死 demo 密码常量
2. 生产环境重建 `web` 时，如果执行 `docker compose -f infra/docker-compose.yml ...` 而没有显式传入 `--env-file .env`，由于 compose 文件位于子目录，`web` 容器会回退到 compose 默认 demo 凭据，并把旧值写进 `/config.js`

这类值同时影响：

- 前端展示与快捷填充行为
- 后端鉴权实际接受的账号密码
- 生产环境可运维性

如果继续把这类值散落在前端源码常量中，后续只要调整 demo 账号或部署命令，就会再次出现“页面看起来有功能，但实际不可用”的假通过状态。

## 决策

本项目后续采用以下长期规则：

1. 凡是前端需要显示、填充或判断，但又必须与后端运行时保持一致的值，不允许只写在前端源码常量中
2. 这类值统一通过前端运行时配置注入：
   - `web` 容器启动时写入 `/config.js`
   - 前端通过独立运行时配置模块读取
3. demo 账号邮箱与密码属于运行时配置，不再视为纯前端常量
4. 生产环境所有 compose 发布命令必须显式使用：
   - `docker compose --env-file .env -f infra/docker-compose.yml ...`
5. 只要本轮改动涉及登录入口、demo 凭据或其他运行时前端配置，发布后必须额外验证：
   - `https://campusbook.top/config.js`
   - 学生 demo 登录接口返回 `200`
   - 管理员 demo 登录接口返回 `200`

## 明确不采用的方案

本轮明确不采用以下做法：

- 继续把 demo 账号密码硬编码在前端组件或工具文件里
- 只依赖 `.env` 构建时注入前端 bundle，而不保留运行时可替换能力
- 认为“页面按钮存在”就等于功能已经真实可用，而不校验运行时配置和接口响应
- 依赖人工记忆 `docker compose` 的当前工作目录和默认 env 行为

这些方案的问题在于，它们会把“可见 UI”与“真实运行时行为”拆开，导致问题只能在上线后才暴露。

## 影响

正向影响：

- demo 凭据可以只通过环境变量轮换，不再要求改前端源码
- 前端快捷填充与后端鉴权使用同一来源，减少状态漂移
- 运行时配置与 HTTP client 的边界更清晰，保持模块解耦
- 发布验证从“资源是否更新”扩展到“业务入口是否真的可用”

需要注意的影响：

- `/config.js` 中的值属于前端可见运行时配置，不适合放真正敏感的私密凭据
- 后续若引入其他运行时前端配置，应继续通过统一配置模块读取，避免再次分散到页面组件
- 如果未来切换到其他部署拓扑，仍需保留“前端运行时值与后端实际值同源”的原则

## 后续动作

1. 后续新增前端运行时配置时，优先扩展统一配置模块，而不是在页面内直接读全局变量
2. 若未来 demo 账号策略取消，应同步清理本 ADR 对 demo 凭据的专门约束，但保留“运行时同源配置”原则
3. 若要进一步降低人为失误，可补一个统一的生产发布脚本，内部强制带上 `--env-file .env`
