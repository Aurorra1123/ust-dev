# 0014 体育组合预约保留为带解释的次级模式

## 背景

`UTG-005` 的用户反馈指出，体育页里的“组合场地”看起来像是一次预定两个场地，但实际意义不清楚。复查当前实现后，可以确认两个事实：

1. 后端并不是伪能力。体育预约接口真实支持 `resourceGroupId`，提交组合预约时会同时锁定整组成员场地。
2. demo seed 里也已经存在真实组合数据，例如 `Badminton Pair`。问题不在于系统没有能力，而在于前端只展示了组合名称和“几个单元”，没有告诉用户成员是谁、为什么要用、会产生什么效果。

如果直接隐藏组合预约入口，会抹掉系统已经具备的真实能力；但如果继续把它当成和单场地同等强曝光的主路径，又会保留当前“看得见、讲不清”的噪音。

## 决策

本项目对体育组合预约的当前阶段处理方式明确如下：

1. 后端组合预约模型、接口和 demo 数据继续保留，不做删除。
2. 前端仅在当前资源存在组合数据时显示“组合预订”入口。
3. 组合模式在前端视为次级模式，不再只靠一个模糊按钮裸露暴露。
4. 用户切入组合模式后，页面必须明确展示：
   - 组合描述或用途说明
   - 组合包含的成员场地
   - “选择一个时段会同时锁定整组场地”的预约效果
   - “任一成员冲突则整组不可选”的冲突语义
5. 组合目标选择项优先展示成员摘要，而不是仅展示数量。

## 明确不采用的方案

本轮明确不采用以下做法：

- 直接隐藏所有组合预约入口
- 继续沿用“组合名 + 单元数量”的弱表达方式
- 为了补表达问题去改后端 schema 或删除现有组合能力

这些方案分别会造成能力损失、继续制造理解噪音，或把本应在前端解决的问题错误地下沉到模型层。

## 影响

正向影响：

- 用户可以更直观地区分“单场地预约”和“整组场地预约”
- 组合预约保留可演示性，不会因为收口而从产品里消失
- 没有组合数据的资源不再显示无意义入口，页面噪音降低

需要注意的影响：

- 当前只解决了学生端理解问题，还没有提供后台维护组合场地的管理入口
- 若未来组合预约成为高频能力，仍需要评估是否补更强的信息架构和后台配置能力

## 后续动作

1. 若后续继续打磨最终演示，可补“单场地 vs 组合预订”的浏览器级截图或录屏
2. 若未来确认组合预约需要被运营人员维护，应新增独立任务规划资源组合管理工作区
