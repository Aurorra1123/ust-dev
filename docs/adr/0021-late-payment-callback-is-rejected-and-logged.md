# ADR 0021: 迟到支付回调采用“拒绝确认 + 补偿留痕”策略

## 状态

已采纳，实施于 `COMP-002`。

## 背景

比赛整改中的 `COMP-002` 要解决“最后一秒支付与同时过期取消”的幽灵支付问题。当前系统的真实支付实现仍是 `Mock Payment`，但评审关注点不是第三方渠道接入，而是：

- 支付回调与超时取消谁赢
- 同一 `transactionNo` 是否幂等
- 已取消订单是否会被错误改回确认态
- 如果迟到回调出现，系统是否留下清晰补偿证据

## 决策

对于已离开 `PENDING_CONFIRMATION` 的订单，迟到支付回调**不再尝试把订单改回 `CONFIRMED`**。

系统采用以下策略：

1. 订单确认和超时取消都基于 `status + version` 做 CAS。
2. `transactionNo` 继续保持唯一，同一笔 callback 重放只允许一次真实确认。
3. 当超时取消先赢时：
   - 待支付 `PaymentRecord` 会从 `PENDING` 改为 `FAILED`
   - 迟到 callback 返回冲突，不再反向确认订单
   - 同时写入 `PaymentCompensationLog(LATE_CALLBACK_REJECTED)`，记录当时的订单状态、支付状态和交易号

## 理由

- 这条路径是当前最小正确解，不会把 mock 支付流程扩展成复杂的退款状态机
- “取消后又确认”会直接破坏订单状态机的一致性，风险高于收益
- 显式补偿日志比把迟到支付信息埋进通用状态日志更容易答辩和追查
- 后续如果接真实支付渠道，`PaymentCompensationLog` 可以继续承接退款、人工补单或财务核对，而不必推翻现有状态机

## 影响

- 订单状态与支付记录不再出现“已取消后又确认”的脏写
- 系统可以对迟到回调给出稳定且可追溯的处理结果
- 当前阶段没有实现自动退款；补偿只负责留痕，不负责自动回滚资金
