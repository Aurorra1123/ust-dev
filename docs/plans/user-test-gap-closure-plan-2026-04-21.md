## 4. 任务卡

### UTG-001 体育离散时段显示与订单时间文案修正

- 用户反馈：羽毛球允许选择非连续时段，但个人预约记录把多个离散时段压成了一个连续时间段。
- 当前状态：体育预约页已经允许选择多个离散时段，且“已选时段”区域会逐条展示所选槽位；但订单详情中的时间文案仍然使用“第一段开始时间 + 最后一段结束时间”的连续区间逻辑。
- 代码依据：`apps/web/src/ui/pages/sports-page.tsx`、`apps/web/src/ui/pages/order-utils.tsx`
- 目标行为：用户选择 `17:00-18:00` 与 `20:00-21:00` 后，订单列表和订单详情应显示为两个独立时段，而不是 `17:00-21:00`。
- 实施范围：前端订单展示层为主，必要时补充共享格式化工具；后端原始槽位数据当前已具备。
- 验收标准：
  - 体育预约可继续选择多个离散槽位。
  - 订单列表与订单详情显示多个独立时段，格式清楚，不误导为连续占用。
  - 同一订单内仍可正确展示单场地与组合场地模式下的时段信息。
- 备注：这一项优先级高，因为它直接影响用户对预约结果的信任感。

### UTG-002 管理端资源、资源单元、规则的安全删除或归档能力

- 用户反馈：管理员无法删除任何资源、资源单元、规则。
- 当前状态：资源后台与规则后台只有查询、创建、更新、绑定入口，没有删除能力；前端工作区也没有相应交互。
- 代码依据：`apps/api/src/modules/resource/resource.controller.ts`、`apps/api/src/modules/rules/rules.controller.ts`
- 目标行为：管理员可以撤销错误配置，但不能破坏已有订单和历史数据。
- 实施建议：资源与资源单元优先采用“归档 / 停用”而不是物理删除；规则支持停用、解绑或安全删除。
- 实施范围：资源写服务、规则服务、管理端工作区、操作反馈与确认弹窗。
- 验收标准：
  - 管理端存在清晰的“停用 / 归档 / 删除”入口。
  - 如果对象已被未来预约、历史订单或资源绑定引用，系统会阻止危险删除并给出明确原因。
  - 管理员可从界面撤销错误规则或错误资源配置，不需要直接改库。
- 备注：这一项是后台可运营性的基础能力，建议与 `UTG-007` 一起做。

### UTG-003 规则工作区从快照页升级为可配置工作区

- 用户反馈：只能增加预约关闭规则，像“限制 1 小时”这样的规则不能通过界面完成；当前规则工作区存在感弱。
- 当前状态：规则后台已经支持创建、更新、绑定资源，但前端规则工作区目前只有快照展示，没有任何配置入口。
- 代码依据：`apps/api/src/modules/rules/rules.controller.ts`、`apps/web/src/ui/pages/admin/workspaces/rules-workspace.tsx`
- 目标行为：管理员可以在界面中完成规则新建、编辑、启停、资源绑定，不再依赖数据库或临时代码。
- 建议首批支持的规则类型：
  - 最低信用分
  - 最大预约时长
  - 允许用户角色
- 实施范围：规则工作区表单、资源绑定交互、规则状态切换、写操作反馈、基础验证。
- 验收标准：
  - 管理员可在界面上创建一条“最大预约时长 60 分钟”的规则，并绑定到指定资源。
  - 学生对该资源提交超时长预约时，会收到可解释的拦截提示。
  - 管理员可停用、修改并重新绑定规则。
- 备注：这项完成后，当前“规则工作区意义不明”的问题会同步收敛。

### UTG-004 自习空间可视化可用时间视图

- 用户反馈：自习房间也需要像羽毛球场那样的可用时间可视化。
- 当前状态：学术空间页当前只加载资源列表并直接提交预约，没有拉取预约状态，也没有时段网格或占用视图；体育页已经具备时段状态查询和网格展示。
- 代码依据：`apps/web/src/ui/pages/spaces-page.tsx`、`apps/web/src/ui/pages/sports-page.tsx`
- 目标行为：用户在提交自习空间预约前，能直观看到哪个房间、哪个时间段已被占用、关闭或仍可预约。
- 实施范围：学术空间前端页面、资源预约状态查询接入、时间窗展示组件。
- 验收标准：
  - 学术空间页面可展示至少一个明确时间窗内的占用情况。
  - 用户可以先看可用性，再决定开始时间与结束时间。
  - 关闭时段、冲突时段和可预约时段有明确视觉区分。
- 备注：这一项主要提升学生端决策效率，也能减少无效提交。

### UTG-005 组合场地语义澄清与选择体验收口

- 用户反馈：组合场地看起来像是一次预定两个场地，但实际意义不清楚。
- 当前状态：体育页已有“单场地 / 组合场地”切换，但当前只展示组合名称和包含单元数量，没有解释这个组合为什么存在、包含哪些场地、适合什么场景。
- 代码依据：`apps/web/src/ui/pages/sports-page.tsx`
- 目标行为：用户在进入组合场地模式时，能够立刻理解“组合预定”到底意味着什么。
- 建议方向：
  - 如果组合场地确有业务意义，则展示成员场地、使用场景和占用影响。
  - 如果当前 demo 中没有强业务价值，则先隐藏该模式，避免造成理解噪音。
- 验收标准：
  - 进入组合场地模式时，页面清楚展示组合成员及预定效果。
  - 若当前资源没有具备解释性的组合数据，则不显示该模式入口。
  - 用户无需阅读代码或猜测，即可理解是否应使用组合场地。
- 备注：这一项偏产品收口，建议先确认挑战赛展示时是否真的需要“组合场地”。

### UTG-006 英文模式清理与双语收口

- 用户反馈：英文界面仍有部分标题和内容是中文。
- 当前状态：核心页面已经大量接入 `localeText`，但仍存在硬编码中文，尤其集中在首页配置、资源工作区、通知工作区默认文案等区域。
- 代码依据：`apps/web/src/ui/pages/home-page.tsx`、`apps/web/src/ui/pages/admin/workspaces/resources-workspace.tsx`、`apps/web/src/ui/pages/admin/workspaces/notifications-workspace.tsx`
- 目标行为：切到英文模式后，系统界面文案应保持完整英文，不再出现“中英混杂”的半成品状态。
- 实施范围：学生首页、登录页、后台各工作区、默认表单 placeholder、默认示例文案。
- 验收标准：
  - 英文模式下，核心学生页面和后台工作区不出现意外中文界面文案。
  - 仅用户自己输入的中文内容或种子数据正文可保留中文。
  - 所有按钮、标题、空态、错误态、成功态和 placeholder 都能随语言切换。
- 备注：这项更适合做一次系统化审计，而不是边发现边补。

### UTG-007 管理端写操作反馈审计与补齐

- 用户反馈：所有操作都没有提示。
- 当前状态：这条反馈不是“完全成立”。资源创建、资源单元创建、放号规则保存、活动创建等路径已经有统一成功/失败提示，但仍不是所有 mutation 都做到了全覆盖。
- 代码依据：`apps/web/src/ui/pages/admin/components/mutation-state.tsx`、`apps/web/src/ui/pages/admin/workspaces/resources-workspace.tsx`、`apps/web/src/ui/pages/admin/workspaces/activities-workspace.tsx`
- 目标行为：所有后台写操作都具备最小可见反馈，包括进行中、成功、失败，以及必要时的危险操作确认。
- 实施范围：资源工作区、活动工作区、规则工作区、通知工作区、工单工作区。
- 验收标准：
  - 所有后台写操作都有 pending 态。
  - 所有后台写操作都有 success 或 error 反馈。
  - 删除、停用、取消类操作带确认提示或二次确认。
- 备注：这一项应与 `UTG-002`、`UTG-003` 一起规划，避免新写操作继续无提示。

### UTG-008 登录页显示密码开关

- 用户反馈：密码输入框需要“显示密码”选项。
- 当前状态：登录页只有标准 `password` 输入框，没有显隐切换控件。
- 代码依据：`apps/web/src/ui/pages/login-page.tsx`
- 目标行为：用户可切换密码显示状态，降低演示环境和多账号切换时的输入成本。
- 实施范围：登录页表单、按钮文案、可访问性属性。
- 验收标准：
  - 默认隐藏密码。
  - 用户可以点击按钮切换显示或隐藏。
  - 按钮具备中英文文案和可访问性标签。
- 备注：属于低风险的小型改动，可穿插在其他任务中快速完成。

### UTG-009 新增活动表单简化

- 用户反馈：新增活动页面可简化，尤其是票种相关输入。
- 当前状态：当前活动创建表单把标题、地点、描述、总额度、状态、售卖时间、活动时间和“首个票种”都放在一个表单里，首屏理解成本较高。
- 代码依据：`apps/web/src/ui/pages/admin/workspaces/activities-workspace.tsx`
- 目标行为：管理员可以用更少的必要输入创建一个常见活动，再按需要补充进阶配置。
- 建议方向：
  - 默认创建一个“普通票”或“默认票种”。
  - 把高级字段折叠到“进阶设置”。
  - 把“首个票种”从必填改为可选自动生成。
- 验收标准：
  - 管理员创建一个免费单票活动时，必要输入明显少于当前版本。
  - 表单仍保留扩展空间，不损伤现有活动模型。
  - 新建活动后的票种和状态流转仍然正确。
- 备注：该项偏体验优化，不建议早于 `UTG-001` 到 `UTG-004`。

### UTG-010 放号规则的产品定位复审

- 用户反馈：放号规则体验怪，甚至可以考虑优化或删除。
- 当前状态：系统已经实现每天、每周、每月放号规则，后台资源工作区也可配置；但用户层面的感知是“规则存在，但价值和意义不清楚”。
- 代码依据：`apps/web/src/ui/pages/admin/workspaces/resources-workspace.tsx`
- 目标行为：要么保留并讲清楚，要么在当前演示阶段简化，不继续让管理员面对一个难以解释的机制。
- 建议决策选项：
  - 保留：继续强化说明文案、显示“下次放号时间”和适用场景。
  - 简化：默认只保留关闭规则，把放号规则收进高级设置。
  - 隐藏：若挑战赛演示不依赖放号规则，则保留后端能力，前端先不暴露。
- 验收标准：
  - 需要先形成产品结论，再决定是否继续投入开发。
  - 前端最终呈现方式与产品结论一致，不出现“技术上有，用户却看不懂”的中间态。
- 备注：这是一个“先决策、后编码”的项，不建议直接机械开发。

## 5. 回归复测项

### REG-001 新增资源单元链路复测

- 现状判断：从当前代码看，新增资源单元的前后端链路已经接通，不应再是“完全未实现”。
- 需要复测的原因：用户曾明确反馈“无法新增资源单元”，说明可能存在运行时问题、验证问题或刷新问题。
- 2026-04-21 复测结果：已通过。本地 HTTPS 站点下使用管理员链路创建临时资源与资源单元成功，创建响应中可直接看到新增单元；重复单元编码会返回 `409 resource-unit-code-conflict`，错误路径也成立。
- 建议复测内容：
  - 选中已有资源后新增资源单元，观察是否写入成功。
  - 提交后资源结构区域是否即时刷新。
  - 错误场景下是否能看到失败提示。
- 复测结论处理：
  - 如果通过，则从缺陷清单中移出，只保留为已验证事项。
  - 如果失败，则追加一个新的真实缺陷任务，而不是继续口头猜测。

### REG-002 操作提示覆盖率复测

- 现状判断：“所有操作都没有提示”已经不是准确表述，但“不是所有操作都有提示”仍然成立。
- 需要复测的原因：当前不同工作区的覆盖程度不一致，容易在演示时出现“有的操作有反馈，有的没有”的割裂感。
- 2026-04-21 复测结果：先发现真实缺口，再已补齐通过。原本活动状态切换缺少统一反馈，且管理员取消预约、资源停用、规则停用、活动关闭、工单关闭等危险操作缺少确认；现已补齐统一反馈与确认，并重新构建本地 `web` 验证。
- 建议复测内容：
  - 资源创建、资源单元创建、规则保存、活动创建、活动发布、通知保存、工单状态更新。
  - 成功、失败、禁用中三类状态是否都有可见表现。
- 复测结论处理：
  - 对已具备反馈的路径标记为通过。
  - 对缺少反馈的路径回填到 `UTG-007` 的实施清单。
