# 比赛核心缺口收口计划（2026-04-22）

## 1. 文档目的

- 把 `docs/review/2026-04-22-core-topic-review.md` 中已经明确的得分点与失分点收口成正式开发计划。
- 明确下一阶段不平均用力，而是优先补最大失分项：支付闭环、幽灵支付、规则引擎扩展与非功能证据。
- 为后续任务拆解、阶段汇报和答辩准备提供统一入口，避免继续依赖聊天记录恢复上下文。

## 2. 当前判断摘要

- 已经命中赛题核心的部分：
  - 多态空间建模
  - 学术空间连续时间与数据库层 `5` 分钟缓冲约束
  - 体育设施离散 slot 与组合资源预约
  - 活动高并发抢票骨架
  - DevOps 一键拉起基线
- 当前最大失分项：
  - 订单支付闭环没有真正进入主链路
  - 幽灵支付只存在骨架，没有真实对撞闭环
  - 规则引擎仍偏“最小可配置版”
  - 前端 a11y / 性能 / 安全 缺少更硬的实现与留证
  - 自动化测试不足，`pnpm test` 尚未承担真实业务回归

## 3. 计划原则

1. 不重写已经基本得分的建模、约束和高并发骨架，只补验证证据和闭环缺口。
2. 先唤醒一条真实付费主链路，再扩展到更广范围，避免为了“全覆盖”把现有稳定链路全部搅乱。
3. 规则引擎继续沿用“规则表 + 执行器”方向，但升级为可注册 handler，不在本阶段引入 DSL 或脚本平台。
4. 前端本阶段不重做视觉，重点补键盘可达性、语义化、性能证据和基础安全硬化。
5. 所有新增比赛收口任务都要落到 `feature-list.json`，并且要求可验证、可留证。

## 4. 统一业务样例

下一阶段以一个固定样例串起付费活动、待支付订单、支付回调、超时取消与最终验证：

- 活动名：`红鸟音乐节`
- 票种名：`普通票`
- 售价：`5` 元，即 `priceCents = 500`

该样例的作用不是替代通用模型，而是作为统一演示与自动化验证入口：

- 管理端可创建一个真实的低价付费活动票种
- 学生端可走“抢票成功 -> 待支付 -> mock 支付 -> 已确认”的完整链路
- 系统级测试可稳定构造“最后一秒支付 vs 超时取消”的幽灵支付对撞场景
- judge / 验收文档可以围绕同一个样例留证，降低演示与答辩成本

## 5. 任务卡

### COMP-001 以红鸟音乐节 5 元门票唤醒付费活动票主链路

- 优先级：`P0`
- 目标：把现有“高并发抢票成功后直接确认”的付费活动票流程改成真实 `PENDING_CONFIRMATION` 主链路。
- 范围：
  - 仅对 `priceCents > 0` 的活动票启用支付闭环
  - 创建订单时写入 `expireAt`
  - 同步写入 `PaymentRecord(PENDING)`
  - 提供 mock 支付发起与 mock 回调入口
  - 免费票可继续走现有直接确认链路
- 验收重点：
  - `红鸟音乐节` 的 `5` 元普通票能够进入待支付状态
  - 订单详情能看到剩余支付时间和支付状态
  - 付费票不再在创建时直接写成 `CONFIRMED`

### COMP-002 幽灵支付对撞保护与补偿闭环

- 优先级：`P0`
- 目标：把订单状态机从“有状态枚举和延迟任务”补成“能真实处理支付成功与超时取消竞争”的闭环。
- 范围：
  - 支付回调与超时取消都基于 `status + version` 做 CAS
  - `transactionNo` 唯一且回调幂等
  - 迟到支付回调在订单已取消时被拒绝或进入补偿分支
  - 支付日志、状态日志、补偿日志可追溯
- 验收重点：
  - `红鸟音乐节` 订单在“最后一秒支付 + 同时过期取消”场景下只有一个最终状态迁移成功
  - 不出现“已取消后又确认”或“已扣款但状态仍脏”的最终数据
  - 存在明确的系统级验证证据

### COMP-003 规则引擎 v2：资格、额度、惩罚进入真实链路

- 优先级：`P1`
- 目标：把当前规则系统从“最小可配置版”升级为更接近比赛答辩要求的真实规则平台。
- 范围：
  - 执行器升级为可注册 handler registry
  - 首批高价值规则覆盖：
    - 活动报名资格
    - 爽约扣分
    - 可预约次数 / 可预约总时长限制
  - `UserCreditLog` 与 `UserRuleProfile` 进入真实链路
  - 不把新增规则继续堆进主流程 service 的 `if-else`
- 验收重点：
  - 至少两类新规则可以通过“新增 handler + 配置”接入，而不是修改主流程核心判断
  - 活动资格与爽约处罚可从配置侧控制
  - 有自动化验证或等价留证

### COMP-004 前端非功能收口：a11y、性能、安全

- 优先级：`P1`
- 目标：补齐评委会追问的非功能项，不再只停留在“页面能用”。
- 范围：
  - 学术空间和体育预约主路径支持键盘操作
  - 关键状态不只靠颜色表达
  - 补焦点态、错误提示、屏幕阅读器文案
  - API / Nginx 增补基础安全头与 CSP 策略
  - 对核心页面补 Lighthouse / Web Vitals / WCAG 留证
- 验收重点：
  - 至少三个核心页面具备可追溯的 a11y / 性能 / 安全验证记录
  - 核心预约路径可纯键盘完成
  - 非颜色语义表达成立

### COMP-005 真实业务测试与评委回归证据

- 优先级：`P1`
- 目标：让 `pnpm test` 不再空跑，并把比赛核心得分点纳入自动化回归。
- 范围：
  - API 集成测试覆盖：
    - 学术空间 `5` 分钟缓冲冲突
    - 体育组合预约原子失败
    - 活动重复报名与不超卖
    - 幽灵支付对撞
    - 规则执行
  - judge smoke 扩展 `红鸟音乐节 5 元门票` 的待支付到确认主链路
  - `docs/verification/` 留下最终验收样例
- 验收重点：
  - `pnpm test` 能执行真实业务测试
  - 核心比赛点存在自动化回归入口
  - 评委可围绕统一样例复现关键链路

## 6. 推荐执行顺序

1. 先做 `COMP-001` 与 `COMP-002`，优先补最大失分点。
2. 再做 `COMP-003`，把规则系统从“像有”补到“真的能答辩”。
3. 最后做 `COMP-004` 与 `COMP-005`，形成非功能和验收证据闭环。

## 7. 当前明确不做的事

- 现在不接第三方真实支付渠道；比赛阶段以 mock 支付证明状态机与并发一致性即可。
- 现在不把所有预约都改造成待支付订单；先用付费活动票打通主链路，风险和投入都更可控。
- 现在不重做整站视觉；当前主要问题不是美术风格，而是高分核心点闭环不足。
- 现在不把规则引擎升级成 DSL；优先做强类型规则与 handler registry。

## 8. 本文档的使用方式

- 要继续排期时，直接对照第 `5` 节任务卡和第 `6` 节执行顺序。
- 要准备评委答辩时，优先围绕第 `4` 节统一样例做演示与留证。
- 要开始实际开发时，同步参考 `feature-list.json` 中新增的 `COMP-*` 项，并按完成情况更新进度记录。
