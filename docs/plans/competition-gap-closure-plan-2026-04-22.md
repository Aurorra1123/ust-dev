## 2. 当前统一判断

- 已经命中赛题核心的部分：
  - 多态空间建模
  - 学术空间连续时间与数据库层 `5` 分钟缓冲约束
  - 体育设施离散 slot 与组合资源预约
  - 活动高并发抢票骨架
  - `Docker Compose` 一键拉起基线
- 当前最大失分项：
  - 订单支付闭环没有真正进入主链路
  - 幽灵支付只存在骨架，没有真实对撞闭环
  - 活动库存一致性、补偿与 `totalQuota` 口径没有独立收口
  - 规则引擎仍偏“最小可配置版”
  - 前端 a11y / 性能 / 安全 缺少更硬的实现与留证
  - 自动化测试不足，`pnpm test` 尚未承担真实业务回归

## 3. 已冻结边界

1. 不重写已经基本得分的建模、约束和高并发骨架，只补验证证据和闭环缺口。
2. 支付闭环先只打通“付费活动票”一条真实主链路，不把学术和体育预约一并改造成待支付订单。
3. 支付阶段只采用 `Mock Payment`，不接第三方真实支付渠道。
4. 规则引擎继续沿用“规则表 + 执行器”方向，但升级为可注册 handler registry，不引入 DSL 或脚本平台。
5. 前端阶段不重做整站视觉，重点补键盘可达性、语义化、性能证据和基础安全硬化。
6. 为避免重写历史记录，保留现有 `COMP-001` ~ `COMP-005` 语义不变，新增 `COMP-006` 承接“活动库存一致性与 totalQuota”这一块独立开发工作。
7. 比赛阶段冻结活动总额度规则为 `totalQuota == sum(ticket.stock)`，不再保留 `>=` 与 `==` 并存的解释空间。

## 4. 统一业务样例

下一阶段继续使用固定样例串起支付、状态机、测试和答辩：

- 活动名：`红鸟音乐节`
- 票种名：`普通票`
- 售价：`5` 元，即 `priceCents = 500`

该样例的作用不是替代通用模型，而是作为统一演示与自动化验证入口：

- 管理端可创建一个真实的低价付费活动票种
- 学生端可走“抢票成功 -> 待支付 -> mock 支付 -> 已确认”的完整链路
- 系统级测试可稳定构造“最后一秒支付 vs 超时取消”的幽灵支付对撞场景
- judge / 验收文档可以围绕同一个样例留证，降低演示与答辩成本

## 5. 六个不重叠工作包

### COMP-001 以红鸟音乐节 5 元门票唤醒付费活动票主链路

- 优先级：`P0`
- 这一包只解决“如何让付费活动票真实进入待支付态”，不负责处理幽灵支付补偿、库存自愈或规则扩展。
- 范围：
  - 仅对 `priceCents > 0` 的活动票启用支付闭环
  - 创建订单时写入 `expireAt`
  - 同步写入 `PaymentRecord(PENDING)`
  - 提供 mock 支付发起、查询与回调入口
  - 免费票继续走现有直接确认链路
- 不在本包处理：
  - 迟到支付回调补偿
  - Redis 库存自愈与 `totalQuota`
  - 规则处罚闭环
- 验收重点：
  - `红鸟音乐节` 的 `5` 元普通票能够进入待支付状态
  - 订单详情能看到剩余支付时间和支付状态
  - 付费票不再在创建时直接写成 `CONFIRMED`

### COMP-002 幽灵支付对撞保护与补偿闭环

- 优先级：`P0`
- 这一包只解决“支付回调与超时取消谁赢、怎么幂等、如何补偿”，不再负责把待支付主链路从零搭起来。
- 前置依赖：
  - `COMP-001`
- 范围：
  - 支付回调与超时取消都基于 `status + version` 做 CAS
  - `transactionNo` 唯一且回调幂等
  - 迟到支付回调在订单已取消时被拒绝或进入补偿分支
  - 支付日志、状态日志、补偿日志可追溯
- 不在本包处理：
  - 活动库存 Redis 对账与冷恢复
  - 规则执行器改造
  - 前端 a11y / 性能留证
- 验收重点：
  - `红鸟音乐节` 订单在“最后一秒支付 + 同时过期取消”场景下只有一个最终状态迁移成功
  - 不出现“已取消后又确认”或“已扣款但状态仍脏”的最终数据
  - 存在明确的系统级验证证据

### COMP-006 活动库存一致性与 `totalQuota` 收口

- 优先级：`P0`
- 这一包是本次收束后新增的独立 backlog，用来承接原先散落在验收结论和 PDF 整改计划里的活动高并发库存问题。
- 范围：
  - 冻结活动总额度规则为 `totalQuota == sum(ticket.stock)`，并在创建/更新活动时做强校验
  - 重写 Redis pending 占位与归属校验，禁止无主补偿
  - 增加库存冷恢复、对账与异常回查
  - 把“绝不超卖”从预扣骨架补成可恢复、可追责、可验证的闭环
- 不在本包处理：
  - 订单待支付主链路
  - 幽灵支付补偿
  - 规则处罚与信用分
- 验收重点：
  - 并发超库存时，数据库中 `reserved` 永远不超过 `stock`
  - Redis 冷丢失后不会虚增可售库存
  - 售罄后热点请求不会持续冲击数据库
  - `totalQuota` 始终严格等于 `sum(ticket.stock)`，不存在双口径解释

### COMP-003 规则引擎 v2：资格、额度、惩罚进入真实链路

- 优先级：`P1`
- 这一包只解决“规则如何扩展并真实接管资格与处罚”，不承担支付和活动库存收口职责。
- 前置依赖：
  - `COMP-001`
  - `COMP-002`
- 范围：
  - 执行器升级为可注册 handler registry
  - 首批高价值规则覆盖：
    - 活动报名资格
    - 爽约扣分
    - 可预约次数 / 可预约总时长限制
  - `UserCreditLog` 与 `UserRuleProfile` 进入真实链路
  - 新增规则不再继续堆进主流程 service 的 `if-else`
- 不在本包处理：
  - `Mock Payment` 主链路
  - 活动库存补偿与 `totalQuota`
  - 前端响应式整改
- 验收重点：
  - 至少两类新规则可以通过“新增 handler + 配置”接入，而不是修改主流程核心判断
  - 活动资格与爽约处罚可从配置侧控制
  - 有自动化验证或等价留证

### COMP-004 前端非功能收口：a11y、性能、安全

- 优先级：`P1`
- 这一包只负责前端非功能和留证，不负责补业务状态机、库存或规则后端能力。
- 前置依赖：
  - `COMP-001`
  - `COMP-002`
- 范围：
  - 学术空间和体育预约主路径支持键盘操作
  - 关键状态不只靠颜色表达
  - 补焦点态、错误提示、屏幕阅读器文案
  - API / Nginx 增补基础安全头与 CSP 策略
  - 对核心页面补 Lighthouse / Web Vitals / WCAG 留证
- 不在本包处理：
  - 订单状态机核心逻辑
  - 活动库存一致性
  - 规则 handler registry
- 验收重点：
  - 至少三个核心页面具备可追溯的 a11y / 性能 / 安全验证记录
  - 核心预约路径可纯键盘完成
  - 非颜色语义表达成立

### COMP-005 真实业务测试与评委回归证据

- 优先级：`P1`
- 这一包只负责把前面工作包产物转成自动化门槛和验收证据，不代替前置业务包本身的实现。
- 前置依赖：
  - `COMP-001`
  - `COMP-002`
  - `COMP-006`
  - `COMP-003`
- 范围：
  - 先以前置 `Guardrail-0` 方式落地保护性回归，用于保住当前已命中的学术缓冲、体育 slot/组合语义与活动报名唯一性
  - API 集成测试覆盖：
    - 学术空间 `5` 分钟缓冲冲突
    - 体育组合预约原子失败
    - 活动重复报名与不超卖
    - 幽灵支付对撞
    - 规则执行
  - 系统级异步与部署测试覆盖：
    - `judge-up` 幂等
    - worker / delayed job 恢复
    - Redis 库存恢复与异常可发现
  - smoke / judge 至少覆盖：
    - 一次学术预约
    - 一次体育预约
    - 一次活动抢票
    - 一次订单取消或确认
    - 一次规则命中
  - judge smoke 扩展 `红鸟音乐节 5 元门票` 的待支付到确认主链路
  - `docs/verification/` 留下最终验收样例
- 不在本包处理：
  - 通过写测试替代业务修复
  - 补规则平台本身
  - 补前端 UI 结构重构
- 验收重点：
  - `Guardrail-0` 先行落地，确保进入支付与库存整改前，当前强项已有保护性回归
  - `pnpm test` 能执行真实业务测试
  - `judge-up` 连续执行保持幂等，worker / 延迟任务 / 库存恢复失效时能被自动发现
  - smoke / judge 不再只测首页与登录，而是覆盖学术、体育、活动、订单和规则命中
  - 评委可围绕统一样例复现关键链路

## 7. 当前明确不做的事

- 现在不接第三方真实支付渠道；比赛阶段以 mock 支付证明状态机与并发一致性即可。
- 现在不把所有预约都改造成待支付订单；先用付费活动票打通主链路，风险和投入都更可控。
- 现在不重做整站视觉；当前主要问题不是美术风格，而是高分核心点闭环不足。
- 现在不把规则引擎升级成 DSL；优先做强类型 handler registry。

## 8. 使用方式

- 要继续排期时，直接对照第 `5` 节工作包与第 `6` 节执行顺序。
- 要准备评委答辩时，优先围绕第 `4` 节统一样例做演示与留证。
- 要开始实际开发时，同步参考 `docs/plans/feature-list.json` 中的 `COMP-*` 项，并在每完成一个工作包后更新 `docs/progress/agent-progress.md`。
