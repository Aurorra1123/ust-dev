# 最后阶段冲分计划（2026-04-22）

## 1. 文档定位

本文用于收口当前项目在最终答辩前最值得优先修补的高收益项。

目标不是继续扩功能面，而是围绕评委最容易当场验证、最容易当场追问、最容易直接扣分的点做最后阶段修补。

视频准备暂不纳入本文。

## 2. 使用原则

1. 只修高收益缺口，不做大范围重构。
2. 先修会直接丢分的硬伤，再补量化证据和答辩材料。
3. 所有修改都必须能映射到赛题硬要求，不做“看起来很忙但不涨分”的工作。
4. 不新增重型基础设施，不引入新的复杂依赖。
5. 不通过写更多文档替代真实修复；文档只承接已完成或即将完成的高收益动作。

## 3. 当前判断

当前项目已经命中赛题主干，但距离“终审稳拿高分”仍有几处明显缺口：

- 自动化验收不是全绿
- 学术空间缓冲实现与题面字面要求不完全一致
- API 容器镜像不满足“多阶段 Dockerfile”硬要求
- 前端无障碍与性能缺少量化证据
- 部分学生侧表单仍存在低成本可修的可访问性缺口
- 前端主包偏大，路由没有进行最小拆分
- 规则引擎实现虽然已脱离核心 if-else，但对题面“责任链或表达式引擎”的答辩口径还不够强

## 4. 最终执行顺序

1. 修自动化红灯
2. 修学术空间缓冲语义
3. 补 API 多阶段 Dockerfile
4. 固化极端边界演示证据
5. 补前端量化证据
6. 修低成本 a11y 缺口
7. 做最小路由懒加载
8. 补规则引擎答辩说明

## 5. 八个冲分包

### BOOST-001 自动化红灯清零

#### 目标

把当前最硬的工程扣分项先消掉，确保 `pnpm test` 能作为真实验收门槛成立。

#### 当前问题

- 当前自动化并非空跑，但至少存在一条失败用例
- `COMP-001` 第一条付费活动待支付链路用例出现 `404`
- 这会直接影响终验可信度与 CI 说服力

#### 执行动作

1. 定位失败是测试时序问题还是主链路不稳定
2. 重点排查活动 worker 完成、队列清空、订单状态可查询三者之间是否存在时间窗
3. 若问题在测试等待策略，则把 `COMP-001` 对齐到和 smoke 一样的状态轮询方式
4. 若问题在主链路，则修正活动报名异步建单与状态查询的同步边界
5. 重新以根级 `pnpm test` 作为验收口径核对结果

#### 关键触点

- `apps/api/test/comp-001-paid-activity-payment.test.ts`
- `apps/api/test/integration-harness.ts`
- `apps/api/src/modules/activities/activity-registration.service.ts`
- `apps/api/src/modules/activities/activity-registration-worker.service.ts`

#### 完成标准

- `pnpm test` 全绿
- 付费活动票待支付链路不再出现偶发 `404`
- CI 的 `Test` 阶段具备真实可信度

### BOOST-002 学术空间缓冲语义对齐题面

#### 目标

让学术空间预约实现与“前后各 5 分钟隐形缓冲”的题面要求完全一致，避免被评委抓住字面硬伤。

#### 当前问题

- 当前代码里学术预约前缓冲写成 `0`
- 冲突预检虽然使用双向 `±5` 分钟判断，但返回字段与落库语义不完整

#### 执行动作

1. 把学术预约创建链路中的 `bufferBeforeMin` 改为 `5`
2. 校对订单项、预约实体、响应结构中的前后缓冲字段
3. 回归 `11:04` 冲突与 `11:05` 放行边界
4. 更新相关验证记录中的返回示例和描述

#### 关键触点

- `apps/api/src/modules/reservation/reservation.service.ts`
- `apps/api/test/guardrail-0.test.ts`
- `docs/verification/2026-04-22/qa-001-guardrail-0-api-regressions.md`

#### 完成标准

- 学术预约真实落库与接口返回都体现前后各 `5` 分钟
- 缓冲边界行为与既有 guardrail 一致
- 评委无法再通过字段语义质疑该项实现

### BOOST-003 API 镜像改为真正多阶段构建

#### 目标

补齐题面中“多阶段 Dockerfile”的硬要求，让容器化交付更完整。

#### 当前问题

- 当前 `infra/docker/api.Dockerfile` 为单阶段镜像
- 这在最终验收里属于可直接扣分的工程项

#### 执行动作

1. 将 API Dockerfile 拆分为 `builder` 与 `runner` 两阶段
2. `builder` 负责安装依赖、生成 Prisma Client、编译产物
3. `runner` 只保留运行时所需文件和依赖
4. 确认 API 与 worker 仍可共用运行镜像
5. 确认 `docker compose` 与 `judge-up` 路径不受影响

#### 关键触点

- `infra/docker/api.Dockerfile`
- `infra/docker-compose.yml`
- `scripts/judge-up.sh`

#### 完成标准

- API Dockerfile 明确采用多阶段
- judge 与常规 compose 路径不回退
- 镜像结构在答辩中可直接解释

### BOOST-004 固化极端边界演示证据

#### 目标

把最值钱的边界场景整理成一份可直接照着演示的证据文档，降低现场答辩失误概率。

#### 执行动作

1. 新增一份最终阶段边界演示文档
2. 固定以下高收益演示项：
   - 学术 `11:04` 冲突
   - 学术 `11:05` 放行
   - 体育组合资源任一成员冲突整单失败
   - 付费活动票待支付生成
   - 幽灵支付对撞
   - 爽约转 `NO_SHOW` 并触发扣分与禁用
3. 每个场景明确：
   - 前置数据
   - 操作步骤
   - 关键接口或页面
   - 预期结果
   - 现场讲解重点

#### 关键触点

- `docs/verification/2026-04-22/`
- 现有 `guardrail`、`comp-002`、`comp-003`、`qa-007` 留证文档

#### 完成标准

- 形成一份无需临场组织就能直接演示的脚本型证据
- 现场展示时可以优先打最能得分的边界，而不是只演 happy path

### BOOST-006 修学生侧低成本 a11y 缺口

#### 目标

用最小改动补掉最容易被现场抓住的可访问性缺口。

#### 当前问题

- 部分学生侧表单仍主要依赖 placeholder
- 其中工单页最明显

#### 执行动作

1. 优先排查学生主路径中的裸 `input` / `textarea`
2. 为缺少语义标签的字段补充显式 `label`
3. 补必要的 `id`、说明文字与 `aria-describedby`
4. 如存在错误提示，补全与输入框的关联关系

#### 关键触点

- `apps/web/src/ui/pages/service-requests-page.tsx`
- 其他学生端高频表单组件

#### 完成标准

- 学生端核心表单不再依赖 placeholder 充当标签
- 可在答辩时直接说明已修掉低成本显性缺口

### BOOST-007 前端最小路由懒加载

#### 目标

以最小范围改善前端首屏体积与加载策略，缓解单主包过大的问题。

#### 当前问题

- 当前主页面基本都在路由层静态导入
- 现有产物中主 JS 仍是单大包

#### 执行动作

1. 在路由层优先对以下页面做 `React.lazy`：
   - `AdminPage`
   - `SpacesPage`
   - `SportsPage`
   - `ActivitiesPage`
   - `OrdersPage`
   - `OrderDetailPage`
   - `ServiceRequestsPage`
2. 为路由懒加载统一补一个轻量 fallback
3. 构建后记录 chunk 变化与首包变化
4. 将结果纳入前端量化证据文档

#### 关键触点

- `apps/web/src/routes.tsx`
- 相关页面组件

#### 完成标准

- 路由层出现明确分包
- 首页不再加载所有业务页面代码
- 性能答辩口径明显改善

### BOOST-008 补规则引擎答辩说明

#### 目标

在不大改实现的前提下，把现有规则执行框架解释得足够清楚，降低题面字面要求带来的答辩损耗。

#### 当前问题

- 当前实现已经不是主流程堆 if-else
- 但答辩层面对“责任链或表达式引擎”的说服力还不够强

#### 执行动作

1. 新增一份规则引擎说明文档
2. 明确说明：
   - rule handler registry
   - 规则归一化
   - 作用域判断
   - 资源绑定
   - 爽约处罚链路
3. 给出“新增一个新规则类型”的接入步骤
4. 明确当前边界：
   - 不是通用脚本平台
   - 但已经实现可配置、可注册、可扩展，且未把规则散落在核心业务 if-else 中

#### 关键触点

- `apps/api/src/modules/rules/rule-engine.ts`
- `apps/api/src/modules/rules/rules.service.ts`
- `docs/architecture/`

#### 完成标准

- 评委追问规则扩展性时有正式文档可指
- 规则引擎项的答辩损耗降低到“实现形态保守”，而不是“根本没做”

## 6. 计划边界

本文明确不纳入以下工作：

- 接入真实第三方支付
- 重写整个规则引擎为 DSL 或脚本执行器
- 新增业务功能面

- 大范围前端视觉重构
- 视频录制本身

1. 更新 `docs/progress/agent-progress.md`
